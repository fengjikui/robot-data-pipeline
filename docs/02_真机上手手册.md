# 真机遥操作采集上手手册

这是设备到货后的条件化操作指南。来源是固定版本的官方文档和源码，尚未经过本项目真机实测。先完成逐级验收，再进入下一步；具体站立、吊装、急停和负载限制以所购设备的厂商手册与交付培训为准。

## 第零步 核对到货清单

记录订单、铭牌、机器人系统版本、是否为 G1 EDU 29 DoF、手部是否为左右各 7 DoF 的 Dex3、PC2 的 CPU/GPU/内存、网口、头部相机型号和是否已装腕部相机。准备 Vision Pro、独立路由器或交换机、Host、有线网线和可持续写入的磁盘。官方建议 Host 为 x86-64，遥操作 README 测试 Ubuntu 20.04/22.04；本机 Mac 的演示成功不能等价于官方真机 Host 环境受支持。[S01][S05]

头部内置相机与额外立体相机不是同一承诺。腕部 D405、支架、USB3 线材和 PC2 USB 带宽都要单独确认。官方四路相机数据配置默认包含左右头部与左右腕部；只有一台相机时需要修改转换 schema，不能假装四路都存在。

验收产物：`hardware_inventory.json`、设备照片、网络表和相机配置备份。未确认的字段写 unknown。

## 第一步 建立可达网络

以下 IP 仅为官方例子：Host `192.168.123.2`，PC2 `192.168.123.164`。用设备实际设置替换，避免与现有网络冲突。Host 和机器人优先有线连接；Vision Pro 连到可访问 Host 与 PC2 的 Wi-Fi。确认没有 AP 客户端隔离或阻断 DDS 的网络策略。

在 Host 上执行：

```bash
ip -br addr
ip route
ping -c 3 192.168.123.164
```

使用厂商交付的账户访问 PC2；本文不提供或依赖默认密码。能 ping 通只证明 IP 可达，不证明相机端口、WebSocket 或 DDS 状态订阅成功。再分别验证相机客户端和只读 SDK 状态。记录 Host 网卡名，启动时显式传 `--network-interface`，防止 SDK 选错网卡。

验收：能独立看到 PC2、相机帧与关节状态，且机器人尚未由本项目发送动作。

## 第二步 安装固定版本的 Host 软件

这些命令应在 Ubuntu Host 上执行，不是在 Vision Pro 或机器人底层控制单元上执行。

```bash
conda create -n tv python=3.10 pinocchio=3.1.0 numpy=1.26.4 -c conda-forge
conda activate tv
git clone https://github.com/unitreerobotics/xr_teleoperate.git
cd xr_teleoperate
git checkout 817fb00c63cde15e5f24a0f8fa08e1e33ed89d3b
git submodule update --init --recursive
cd teleop/teleimager
pip install -e . --no-deps
cd ../televuer
pip install -e .
```

`--no-deps` 不会自动解决 teleimager 依赖；继续按它的 README 安装与当前 PC2 相机匹配的库。SDK 在单独目录安装：

```bash
git clone https://github.com/unitreerobotics/unitree_sdk2_python.git
cd unitree_sdk2_python
pip install -e .
git rev-parse HEAD
```

官方要求 SDK 不早于 `404fe44d76f705c002c97e773276f2a8fefb57e4`。当前未对 SDK 的新旧组合做真机验收，不能仅取最新版本就宣称兼容；到货后将验证过的 revision、CycloneDDS 配置及依赖版本写入环境记录。不同用途用不同环境：遥操作 `tv`、训练 `unitree_lerobot`、仿真 `unitree_sim_env`。

## 第三步 设置 Vision Pro 的可信连接

官方 XR_Device Wiki 记录过 Vision Pro 的 visionOS 2.3.2 验证情况，这不是对所有更新版本的兼容承诺。结合当前 visionOS/Safari 检查 WebXR 会话与权限。页面标签和实验功能随系统版本变化，需要记录实际版本；不要假定安装一个原生 App 就会自动运行本方案。当前方案通过 Safari XR 页面传头手信息。[S06]

在 Host 的 `teleop/televuer` 中按官方 README 生成 CA 与服务端证书，服务端证书的 subjectAltName 至少包含实际 Host IP；若同一证书也用于 PC2 图像服务，还要包含 PC2 IP。完整可复制命令保存在 `scripts/visionpro_cert_template.sh`。把根证书传至 Vision Pro 并按其设置完成安装与信任；私钥留在受控机器中。证书 IP 与 URL 不匹配会导致 WSS 或 WebRTC 连接失败。

访问例子：

```text
https://192.168.123.2:8012/?ws=wss://192.168.123.2:8012
```

8012 是当前 televuer 页面入口。PC2 头部相机启用 WebRTC 时，官方先用 `https://192.168.123.164:60001` 检查并信任相机服务证书；60001 是当前示例端口，实际以服务配置为准。先在局域网内验证，不要把这些开发服务直接暴露到公网。

验收：Safari 能进入 XR 会话，Host 终端显示 WebSocket 连接，图像持续更新，手腕和手部输入可见。显示正常不代表已向机器人发送动作。

## 第四步 在 PC2 启动相机服务

在 PC2 按其架构安装适当环境。以下模板对应已经有 conda 的 PC2，安装 UVC/RealSense 依赖前核对交付系统要求：

```bash
conda create -n teleimager python=3.10
conda activate teleimager
sudo apt install libusb-1.0-0-dev libturbojpeg-dev
git clone https://github.com/unitreerobotics/teleimager.git
cd teleimager
git checkout 57cf2a40572227273fa001cd17833b755331ec97
pip install -e ".[server]"
bash setup_uvc.sh
teleimager-server --cf
```

按官方方式配置 `teleimager`，并保存 `cam_config_server.yaml`。逐一匹配头部、左右腕部设备 ID、分辨率、立体拼接方式、FPS、ZMQ/WebRTC 开关；不要把 Linux 枚举顺序当成永久的左右相机标识。[S01]

```bash
# 运行位置 PC2 的 teleimager 环境
teleimager-server
# 等价入口
python -m teleimager.image_server
```

Host 上使用图像客户端检查：

```bash
python -m teleimager.image_client --host 192.168.123.164
```

观察实际帧更新，遮挡左腕相机验证左右对应，检查快动作是否出现明显延迟或旧帧重复。Dex3 与 Inspire 的软件链不同；不要因为 README 有 Inspire 服务命令就给 Dex3 随意增加不需要的串口桥。

验收：保存相机配置、短视频、相机顺序和丢帧检查记录。

## 第五步 先做单关节和静止双臂验证

依照交付培训完成机器人支撑、站立和急停验证。有人专门负责急停和观测。先不带箱子，确认控制模式和启动姿态，操作者手臂与机器人初始姿态对齐。

在 Host 的 `xr_teleoperate/teleop` 目录中，先运行 `python teleop_hand_and_arm.py --help`。以下是 G1 29 + Dex3 的命令模板，网卡名必须替换：

```bash
python teleop_hand_and_arm.py \
  --arm G1_29 --ee dex3 --input-mode hand \
  --img-server-ip 192.168.123.164 \
  --network-interface enp3s0 \
  --frequency 30 --record \
  --task-dir /data/robot_raw \
  --task-name box_transfer \
  --task-goal "Move the box from table A to table B." \
  --task-desc "Fixed-base grasp and place pilot." \
  --task-steps "approach; grasp; lift; place; release"
```

这是普通低层双臂命令模板，只有在厂商确认对应模式、支撑与控制权之后才执行。程序启动后按当前 README 的 `r` 开始遥操作，`s` 开始录制，再按 `s` 停止并保存一回合；退出按当前提示执行，等待写入完成。中途强行杀进程可能留下不完整 JSON 或缺图。

验收：手部开合方向、关节正负方向、手腕坐标变换都正确；录到一个短静止 episode 和一个慢速双臂 episode，文件可读且图片齐全。

## 第六步 单独验证移动协同

官方 `--motion` 允许与运动控制程序协同，手追踪可由 R3 控制常规行走，当前 README 仅支持 Regular mode。它改变控制主题和控制权，不能只为了“能够走路”随手给上一条命令追加参数。[S01][S02]

关键验收不是机器人肉眼走动，而是检查数据文件是否记录了训练需要的 `base_command`、本体状态、腰部状态、时间与控制模式。当前普通 Dex3 转换器忽略 `body`。在移动数据契约完成前，先把行走作为现成控制器能力，学习双臂操作；如果目标是学习全身移动，则设计新的记录器和全身 exporter。

## 第七步 正式采集与逐回合检查

建议先采 5 至 10 个慢速试验回合，完成质检和回放再扩大；这只是工程起步建议，不是保证训练足够的数据量。每个回合记录 task、操作者、物体和桌面配置、成功/失败/中止及原因，失败原始数据保留，训练筛选在索引层完成。

在当前项目运行：

```bash
.venv/bin/python -m robot_pipeline check-raw \
  /data/robot_raw/box_transfer/episode_0001/data.json \
  --report artifacts/episode_0001_quality.json
```

本原型只接受 Dex3 的双臂双手 28 维和 `color_0` 至 `color_3` 四路 640×480 图像；其他配置必须增加适配器，不能靠改文件名通过。它检查结构、有限数值、连续索引、路径和可解码图片，不能自动判定箱子是否掉落或相机是否物理同步。

## 第八步 备份与交接

先结束录制并等待写入，再计算文件哈希并复制原始目录。原始数据只读留存。用临时输出目录做切段、筛选和格式转换。记录 `git rev-parse HEAD`、各环境依赖、相机标定、名义频率和真实时间戳方案。测试集按日期或场景隔离，先确定划分，再生成增强数据，避免同一轨迹的变体进入训练与测试两边。
