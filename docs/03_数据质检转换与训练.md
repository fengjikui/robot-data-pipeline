# 数据质检转换与训练

## 原始记录是什么样子

Host 的 EpisodeWriter 保存 `task/episode_0001/data.json` 和 JPG 图片；一个回合有一个任务说明和按采样顺序排列的 `data` 数组。下面是结构缩写，方括号中的省略号用于讲解，不是合法可训练 JSON。可运行的完整示例见 `examples/raw/schema_fixture/episode_0000/data.json`，它明确标记为合成格式样例。

```json
{
  "info": {"image": {"width": 640, "height": 480, "fps": 30}},
  "text": {"goal": "Move the box from table A to table B."},
  "data": [{
    "idx": 0,
    "colors": {
      "color_0": "colors/000000_color_0.jpg",
      "color_1": "colors/000000_color_1.jpg",
      "color_2": "colors/000000_color_2.jpg",
      "color_3": "colors/000000_color_3.jpg"
    },
    "states": {"left_arm": {"qpos": ["7 measured angles"]}},
    "actions": {"left_arm": {"qpos": ["7 target angles"]}}
  }]
}
```

实际 states 和 actions 都还有 `right_arm`、`left_ee`、`right_ee`，常见分支的每组 `qvel` 与 `torque` 为空。图片以相对路径引用，JSON 不内嵌 RGB 像素。depths、tactiles、audios 和 sim_state 是可选槽；存在字段不代表已经录到了有效深度、触觉或声音。[S03]

## 质量检查应该放在哪里

采集之前检查设备配置、关节名、单位、参考坐标系、相机内外参、左右相机、控制模式、任务成功定义。采集过程中检查帧新鲜度、丢包、控制限幅、队列积压与中止原因。采集之后检查文件可读、图像齐全、有限数值、维度和顺序、连续索引、异常跳变、轨迹和视频是否对齐，以及任务实际是否成功。转换之后再核对行数、episode 数、时间索引、相机数、向量顺序、统计量和加载后的样本。

普通 EpisodeWriter 的逐帧项目包含 idx，没有统一保存所有传感器的采集时间戳。转换器没有实施跨传感器时间对齐。即便 `timestamp = frame_index / 30` 能构造名义时间轴，也无法证明图像和电机反馈来自同一物理时刻。建议到货后增加每路源时间戳、Host 单调接收时间、序号和图像年龄，再量化同步偏差。

例如将“超过一个采样周期的旧帧比例”“图像连续重复比例”“指令和状态延迟”作为监测指标；具体阈值需要按设备实测和任务容忍度设置，不能把任意数值说成厂商规范。不要用重新编号来掩盖缺帧。

## 数据增强的三种层次

1. 训练时视觉增强：小幅亮度、色彩、对比度等。标签一般可保持，但先检查是否破坏任务可观测性。大幅裁剪会切掉箱子或手，不能机械套用。
2. 仿真重渲染：同一有效轨迹下改变光照、背景和相机，在新图像里保持动作对应。官方 sim 提供 replay 与 generate_data；modify_light 和 modify_camera 还需修改相应函数并验证，不是打开开关就完成全面随机化。[S08]
3. 动力学与任务变化：改变质量、摩擦、箱子位置、桌高或路线。必须重新仿真并验证成功，原来的动作不一定仍然正确。动作加噪声和左右镜像必须同时处理所有坐标系和关节映射。

先划分原始 episode，再做增强。一个母回合的所有变体只能出现在同一划分中。训练集合上计算归一化统计量；测试集不参与调阈值与超参数。

## 官方转换脚本到底做了什么

核查文件：`unitree_lerobot/utils/convert_unitree_json_to_lerobot.py`，固定 commit `41c2805742de879ddab2d8d6beaeaf215f876395`。[S04]

`JsonDataset._init_paths` 按两层目录扫描：`raw-dir/task/episode/data.json`。因此 `--raw-dir` 应指向 task 的父目录；直接把一个 task 目录传进去，可能把 episode 内的子文件错误地当成 episode 路径。这与 README 的简短注释容易混淆，必须核对源码与实际目录。

`ROBOT_CONFIGS` 决定提取字段。`Unitree_G1_Dex3` 使用顺序：`left_arm.qpos` 7 → `right_arm.qpos` 7 → `left_ee.qpos` 7 → `right_ee.qpos` 7。同一顺序分别用于 `observation.state` 和 `action`。它默认不取 body、速度、力矩或深度。

相机映射是 color_0 → cam_left_high，color_1 → cam_right_high，color_2 → cam_left_wrist，color_3 → cam_right_wrist。左右手的手指排列并不完全相同，关节名是解释向量的必需元数据，不能只说“28 个浮点数”。[S04]

转换器读取 JPG，用 OpenCV 将 BGR 转成 RGB，再逐帧 `dataset.add_frame` 和逐回合 `save_episode`。任务文本来自 `text.goal`。时间戳和索引由 LeRobot 写入流程生成；此脚本没有把原始采集时间戳传入 add_frame。它硬编码 `fps=30`，图像 schema 硬编码 480×640×3，不自动重采样、不自动纠错、不评估成功。[S04]

## 参数表和可复制模板

完整参数来自函数签名和 DatasetConfig。`evidence/converter_signature_help.txt` 是从固定源码抽取签名后用 tyro 生成的帮助；这验证了参数拼写，未安装完整 LeRobot 环境执行官方转换。

| 参数 | 默认值 | 实际用途 |
| --- | --- | --- |
| `--raw-dir` | 必填 | 包含 task 子目录的原始根目录 |
| `--repo-id` | 必填 | owner/name 标识，也是默认缓存目录的一部分 |
| `--robot-type` | 必填 | 必须与 `ROBOT_CONFIGS` 的键匹配 |
| `--push-to-hub` | false | 默认仅本地；显式启用才上传 |
| `--mode` | video | video 或 image，特征中图像存储类型 |
| `--dataset-config.use-videos` | true | Dataset 创建时的视频选项，需与 mode 一致 |
| `--dataset-config.tolerance-s` | 0.0001 | LeRobot 时间容差，不能修复物理不同步 |
| `--dataset-config.image-writer-processes` | 10 | 写图进程数，本机建议先设 1 |
| `--dataset-config.image-writer-threads` | 5 | 写图线程数，建议先设 1 |
| `--dataset-config.video-backend` | None | 视频读取后端，由具体环境验证 |

没有 `--fps`、`--root`、`--quality-threshold` 或自动动作重定向参数。想改变这些行为，需要修改经过审查的转换代码。普通 README 用下划线拼写部分参数，签名提取的 tyro 帮助采用连字符；执行前仍须在完整环境中运行原脚本 `--help`。

```bash
# 运行位置 Ubuntu 的 unitree_lerobot 仓库根目录
# 每次用新临时目录，避免覆盖已有数据集
TELEOP_CONVERT_RUN=$(mktemp -d /tmp/g1-convert.XXXXXX)
export HF_LEROBOT_HOME="$TELEOP_CONVERT_RUN/lerobot"
python unitree_lerobot/utils/convert_unitree_json_to_lerobot.py \
  --raw-dir /data/robot_raw \
  --repo-id local_report/box_transfer_dex3 \
  --robot-type Unitree_G1_Dex3 \
  --mode video \
  --dataset-config.image-writer-processes 1 \
  --dataset-config.image-writer-threads 1
```

重要的实际行为：脚本两处对已存在的 `HF_LEROBOT_HOME/repo_id` 执行 `shutil.rmtree`。因此本项目的 `plan-convert` 只输出命令方案，默认不执行原脚本。使用新运行目录、保留原始文件，并在确认路径后运行，才能避免缓存目录里旧转换结果被删除。

原脚本会缓存全部 episode 的 JSON，逐 episode 把图像读入内存，再启动写图工作线程。大数据量时不能只根据 GPU 显存估算内存，先测一个 episode 的 RAM 和写盘速度，再分批转换。`mode=image` 与 `use_videos` 是独立参数，不要只改其中一个就认为已验证图像模式。

## 转换后格式长什么样子

LeRobot 用 Parquet 保存时间序列数值和索引，用视频或图像存视觉数据，meta 保存 schema、任务、统计量和 episode 边界。训练读取器把这些组合成张量样本。

v2 常见每 episode 一个 Parquet 和每相机每 episode 一个 MP4；v3 通常按文件大小把多个 episode 放进同一数据或视频分片，episode 的位置与偏移另存于元数据。不能仅凭文件编号推断 episode 编号。

```text
LeRobot v3 示例
meta/info.json
meta/stats.json
meta/episodes/chunk-000/file-000.parquet
meta/tasks.parquet                 # 本次实际 Unitree 数据快照
  或相应版本的 tasks.jsonl         # 不同库版本文档有差异

data/chunk-000/file-000.parquet
videos/observation.images.cam_left_high/chunk-000/file-000.mp4
```

实际路径以固定数据 revision 的 `meta/info.json`、目录树和读取器实现为准。官方数据卡里的旧 v2 示意不能覆盖实际 v3 文件；LeRobot 文档对任务表的展示也可能随版本变化。[S07][S09]

一条加载样本大致是：

```python
{
  'observation.state': Tensor[28],
  'action': Tensor[28],
  'observation.images.cam_left_high': Tensor[3, 480, 640],
  'timestamp': 0.0333,
  'frame_index': 1,
  'episode_index': 0,
  'task': 'Move the box from table A to table B.'
}
```

相机编码前可使用 HWC，读取后常为 CHW。动作 chunk 会形成 `[T_action, 28]`，batch 后为 `[B, T_action, 28]`。不要只看到 meta 的 shape 就猜所有 API 的轴顺序。深度和触觉若要训练，需要在 exporter、schema、读取器和策略四处明确支持。

## 是不是所有模型都能用

格式可以被多个模型共享，动作语义不会自动通用。是否可用要同时满足：读取器支持数据版本；模型支持相机和状态特征；动作维度、单位、参考坐标系和控制含义吻合；时间窗口和频率正确；输出动作可由部署控制器解释。

ACT 与 Diffusion 可以针对同一套双臂双手数据训练。VLA 还需要任务文本、相机重命名、动作适配和相应预训练权重。PPO 这样的在线 RL 除了观察和动作，还需要环境、奖励、终止和在线 rollout；把离线示范转换成 LeRobot 不等于已经得到一个可直接跑 PPO 的环境。

| 训练项 | ACT 例子 | Diffusion 例子 | 含义 |
| --- | --- | --- | --- |
| `policy.type` | act | diffusion | 选算法和架构 |
| 观察窗口 | `n_obs_steps=1` | `n_obs_steps=2` | 使用多少历史观察 |
| 预测长度 | `chunk_size=100` | `horizon=16` | 一次预测多长序列 |
| 执行长度 | `n_action_steps=100` | `n_action_steps=8` | 推理后执行多少步再重算 |
| 数据频率 | 30 Hz | 30 Hz | 时间长度还要除以 Hz |
| 其余 | batch、steps、lr、seed、设备、预训练权重、归一化、训练划分 | 同左 | 决定训练方式与复现条件 |

上表数字是核查版本默认值，不是搬箱最优参数。例如 100 个动作在 30 Hz 对应约 3.33 秒的预测范围；并不要求真机一定连续开环执行 3.33 秒。部署时按当前算法实现选择更新频率和执行长度。[S10]

## 训练环境与命令模板

从 `unitree_lerobot` 固定 commit 递归初始化子模块；它的 LeRobot 固定为 `a5b29d430105f5235eb05bbf2db5a0d747a869d6`，不要直接换成另一个 main 来混用旧参数。按照仓库安装训练依赖后，先做 100 steps 的加载与反传检查，再开始正式训练。下列为未执行的 Ubuntu CUDA 模板，输出目录须为新目录：

```bash
cd unitree_lerobot/lerobot
OMP_NUM_THREADS=1 python src/lerobot/scripts/lerobot_train.py \
  --dataset.repo_id=local_report/box_transfer_dex3 \
  --dataset.root=/data/converted/box_transfer_dex3 \
  --policy.type=act \
  --policy.device=cuda \
  --policy.push_to_hub=false \
  --batch_size=8 --num_workers=1 --steps=100 \
  --output_dir=outputs/box_transfer_act_smoke --seed=42
```

换 Diffusion 时用 `--policy.type=diffusion`，再显式确定 `policy.n_obs_steps`、`policy.horizon`、`policy.n_action_steps`。训练前打印实际观察和动作 key、加载一个 batch、检查图像色彩和动作范围；从训练集生成统计量。正式的评估划分应通过数据筛选或 dataset 配置实现，不能因为命令能启动就认为已排除了数据泄漏。

## 部署不是复制一个权重文件

部署顺序为：原始数据回放和关节映射检查 → 离线预测检查 → 匹配场景仿真闭环 → 固定基座或受支撑真机小范围 → 原地抓放 → 最后加入行走。加载模型配置、预处理与反归一化；以训练时相同的相机和关节名构造观察；明确输出为目标关节角还是别的动作，再用相应 SDK 控制器执行。

官方 `eval_g1.py` 会在交互启动后直接调用双臂控制；README 中“visualization=true”不能解释成只显示不动。不能仅依靠一个未经核实的 `send_real_robot` 参数把它当作安全的离线工具。`eval_g1_sim.py` 同样执行 DDS 指令，仿真与真机在同网时需隔离参与者或网络。当前本地原型不导入宇树 SDK，没有真机发送能力。[S11]
