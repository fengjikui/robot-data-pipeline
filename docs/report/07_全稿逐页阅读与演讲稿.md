## 幻灯片 3（正文 2）真机采集的设备分工

![真机采集的设备分工](../../artifacts/report/full_v14/page-03.png)

### 精讲口述

一次真机示范涉及头显、外部主机和机器人。头显提供头手追踪并显示机器人视角，外部主机负责动作映射、逆运动学和记录；机内 PC2 是独立开发计算单元，本例运行相机服务，运控与关节负责执行和实际状态反馈。[1][2][4]

主机的网线接入机器人交换网络，可分别访问 PC1、PC2。头显通过可互通的无线网络访问服务，图像不一定经过主机。腕部相机属于选配，机内框图只是功能示意，相机与手型等具体配置以到货清单为准。[3][5][6]

### 扩展讲稿与原始出处

这一页先看设备分工。外部有 Apple Vision Pro 和一台我们自己的 Host，另一侧是 G1 机器人。Vision Pro 提供操作者的头、手追踪信息，并显示机器人视角；Host 运行遥操作程序，把人的动作映射成机器人的目标，通过逆运动学求出关节目标，同时记录相机图像、实际状态和目标动作。[1][2]

机器人内部也有独立计算单元。图中的 PC2 是开发计算单元，本例在上面运行 teleimager 相机服务：读取所配置的相机，再把图像提供给 Host 或头显。这里将 PC2 标在躯干内部，表达它是机内的一台独立计算机，框的位置和大小属于功能示意。[1][3]

另一个需要区分的是运控和关节。相机服务与运动控制分别承担职责。Host 可以通过 SDK / DDS 读取实际关节状态；官方手臂控制代码直接订阅 lowstate，并读取关节位置和速度。不能因此画成所有状态先由 PC2 汇总，再转发给 Host。[2][4]

连接上，Host 的一条网线接入机器人的交换网络，因此能够访问运控 PC1 和 PC2。Vision Pro 通过 Wi-Fi 访问可互通网络中的服务。启用 WebRTC 时，头显的图像可以来自 PC2 的图像服务；其他图像模式可能经过 Host。这里先表达设备连接关系，下一页再区分具体的控制、图像和状态通路。[1][3][5]

相机方面，头部视角可以采用内置相机或加装双目方案；腕部相机用于看清手边的操作，属于可选采集设备。43 个自由度不能单独说明已经包含了哪些相机，仍要按到货清单核对。[6]

## 幻灯片 4（正文 3）遥操作过程中的数据流

![遥操作过程中的数据流](../../artifacts/report/full_v14/page-04.png)

### 精讲口述

沿用上一页的设备，数据分成三条通路。控制通路把头手追踪送到 主机，经映射、逆运动学和手部重定向形成目标。图像由 PC2 相机服务提供；启用对应模式时，头显可直接访问其图像服务。实际关节状态则由 主机 通过 DDS 订阅，不必先汇总到 PC2。[1][2][3]

记录时，主机 持续组合图像、实际状态和目标动作。启用遥操作、开始录制、结束录制和写盘完成是不同状态；停止录制以后，还要确认后台保存真正完成，再把有效产物交给下游处理。[4]

### 扩展讲稿与原始出处

这一页沿用刚才的设备位置，换一个角度看数据怎样流动。第一条是控制：Vision Pro 提供头、手姿态，Host 做坐标处理、逆运动学和手部重定向，得到机器人要执行的目标。[1][2]

第二条是图像。PC2 上的相机服务读取相机，Host 订阅图像用于记录。头显也需要看到机器人视角：启用 WebRTC 时可以访问 PC2 的图像服务，其他模式可能经过 Host。图中虚线表示可选显示路径，不能理解成图像永远必须由 Host 转发。[1][2]

第三条是反馈。机器人实际的关节位置和速度通过状态接口发布；Host 的官方手臂控制程序直接订阅 lowstate，因此相机 PC2 不承担所有反馈的必经中转。[3]

最后，Host 把图像、实际状态和发出的目标组合成一条条记录，持续保存为一个回合。开始遥操作、开始录制、结束录制和写盘完成是不同状态。记录器有队列和后台保存过程，所以按下停止录制不应立刻等同于数据已经完整落盘。[4]

### 精讲口述

这一页作为备查，把设备分工对应到实际程序。PC2 运行相机服务，Host 运行遥操作主程序，头显用 Safari 进入 XR 页面。Host 内部组织追踪接收、动作解算、控制和记录等模块。每次先检查基础状态，再开图像服务和主程序，然后连接头显。随动和录制分别触发，结束回合后等待保存完成。具体命令与首次配置条件放在讲稿里。

### 扩展讲稿与原始出处

这页承接设备结构和逻辑数据流，回答“实际在哪台设备启动哪个程序”。主讲时用约半分钟概括即可，命令和详细条件供会后查阅。以下按固定版本的官方说明与源码整理，尚未经过本项目真机验证。G1_29 + Dex3 是参考软件配置，到货后需按实际本体、手部、相机与固件核对。[1][2][3]

一、各设备的程序与职责

1. 机器人运控侧：复用厂商交付的运控与状态服务。它负责执行目标并提供实际关节等状态。此处不给这些基础服务虚构一个 Python 脚本或 systemd 服务名，也不要求每次重新启动整套厂商控制系统。具体运控状态与接管方式以交付文档为准。Host 通过 Unitree SDK / DDS 对应控制与状态接口，关节实际状态无需先由 PC2 的相机服务汇总。[1][3]
2. 机内 PC2：运行 teleimager 的相机服务，读取已配置的头部/腕部相机，按配置使用 ZMQ / WebRTC 发布图像。teleimager-server 与 python -m teleimager.image_server 是同一服务的两种启动入口，任选其一。相机清单、序列号、分辨率、帧率和传输方式由 cam_config_server.yaml 等配置确定。[2]
3. 外部 Host：运行 teleop_hand_and_arm.py。主程序初始化 ImageClient、TeleVuerWrapper、IK、手部重定向/控制、SDK 通信以及开启 --record 后的 EpisodeWriter。televuer、IK 和记录器等是主程序组织的模块，包含相应线程/进程，不意味着用户要手工启动五个独立终端。Host 接收输入、组合实际状态与目标动作、在本地按回合保存。[3][4]
4. Vision Pro：运行 Safari，打开 Host 提供的 HTTPS WebXR 页面，授权头手追踪并进入 XR 会话。按配置取得第一视角图像。WebRTC 配置下，头显还可能直接访问 PC2 的图像页面。这里不预设需要安装一个专用原生 App。[1]
5. AP / 交换网络：提供有线/无线可达性，是基础环境。通常不需要在其上启动自定义采集程序。相机和关节是传感器/执行器，也不各自运行一份 Host Python 程序。

二、首次部署与每次采集分别处理

首次部署需完成软件与子模块版本固定、SDK 安装、Host/PC2 环境准备、网络接口和路由配置、相机配置，以及 Vision Pro 所需证书安装与信任。这些应按官方安装说明逐项完成，不并入每一回合的启动动作。[1][2]

每次采集按下列依赖顺序准备：[1][2][3]

1. 检查设备连接、厂商运控状态、Host 网卡与网络、保存位置及空间。需要用独立只读诊断先确认实际状态可达，不能用启动遥操作主程序来代替只读检查。
2. 在 PC2 开相机服务，确认摄像头配置正确、画面持续更新。必要时用 Host 的独立图像客户端检查视频。确认后可关闭诊断客户端，主程序自身会初始化图像接收。
3. 在 Host 用匹配的本体、手部、PC2 地址、网络接口及记录参数启动主程序。注意：普通非 --motion 路径在等待 r 之前已经涉及 Debug Mode、控制器及命令发布线程初始化，不能理解为“按 r 前只是只读连接”。[3]
4. Vision Pro 连入预定网络，在 Safari 打开对应页面，处理证书与 XR 权限，进入 XR 会话，检查新鲜画面/追踪并按官方流程进行姿态对齐。部分 WebRTC 配置会先访问 PC2 页面检查图像与证书，再进入 Host 页面。[1]
5. 在准备条件满足后按 r 开始随动。只有带 --record 启动时才开启记录能力，r 后按 s 开始回合，再按 s 结束并触发保存。保存由记录器后台处理，需确认保存完成后再录下一回合或退出。q 走正常退出流程，可能包含手臂回零，不能把它等同于硬件急停。[3][4]

三、命令模板（仅供核对，未在真机执行）

PC2，在已安装并配置好的相机环境中：
```bash
conda activate teleimager
teleimager-server
```
等价入口是 python -m teleimager.image_server，不要把两条入口同时启动。若使用 RealSense 等特定相机，按官方配置追加对应选项。[2]

Host，可选的独立图像诊断：
```bash
conda activate tv
python -m teleimager.image_client --host <PC2_IP>
```

Host，双臂/手部参考配置的遥操作与记录模板：
```bash
conda activate tv
cd <XR_REPO>/teleop
python teleop_hand_and_arm.py \
  --arm G1_29 --ee dex3 --input-mode hand \
  --img-server-ip <PC2_IP> --network-interface <HOST_NIC> \
  --frequency 30 --record \
  --task-dir <RAW_ROOT> --task-name box_transfer \
  --task-goal "Move the box from table A to table B."
```

### 精讲口述

这个官方历史回放样本的joint_names只填写了左臂7个名字，但167条记录的实际状态和动作都包含左臂、右臂、左手、右手各7维，共28维，body为空。这里属于名称元数据不完整，不能据此判断只录了左臂，也不能凭维数补造手型与关节名。右侧仍用同一左肩关节说明：state是实际反馈，action是记录的控制目标。原始文件保持原字节，可直接点击查看。

### 扩展讲稿与原始出处

本轮重新遍历了episode_0006全部167条记录：info.joint_names.left_arm有7个名称；right_arm、left_hand、right_hand、body均为空列表。每一条states与actions中的四个臂/手qpos数组均各7项，body均为null。因此元数据命名数量和样本向量维数是不同事实，不能用前者推断是否保存了后者。

### 扩展讲稿与原始出处

## 幻灯片 9（正文 7）增强方法与审查：先小幅试，再验证效果

![增强方法与审查：先小幅试，再验证效果](../../artifacts/report/full_v14/page-09.png)

### 精讲口述

优先试轻量光照和相机退化，再按真实失败原因决定是否加入裁剪、仿真重渲染、重新生成轨迹或生成式编辑。改变物体位置、质量和摩擦后，需要重新执行并记录有效轨迹，不能只改视频沿用旧动作。平台准备保存原始与增强对照，由规则和Agent初筛、人复核，再做相同预算的闭环对照。既看偏移场景是否改善，也看原场景有没有退化，没收益就回退。

### 扩展讲稿与原始出处

可试方法分层：
1. 轻量亮度/对比度/曝光gamma/色温，优先模拟真实部署照明；LeRobot固定版内置部分，其余需自定义。
2. 轻度模糊、噪声、压缩伪影、局部阴影，先测真实相机分布再定强度。
3. 小裁剪、平移和仿射，审查目标/接触是否被裁，像素标注/深度/内参是否需同步处理。不要把二维仿射当真实相机视点变化。
4. 仿真重渲染与灯光/材质变化，要求可恢复物理轨迹和相机。改变物体位姿、摩擦或质量则需重新闭环执行并保存新state/action，Isaac Lab Mimic是现有工具候选。
5. 生成式背景/纹理/干扰物编辑可参考GenAug、ROSIE，但应保护机器人、目标和接触区域，审查多帧/多视角几何。
6. 真实补采与失败恢复回合直接补部署覆盖；语言同义改写只适用于语言条件策略；空间重定向须同时变换状态、动作和几何。它们不是给任意动作向量加噪即可完成的增强。

审核流程是本项目设计：先按母回合/场景留出独立测试，再保存参数、随机种子、母回合、实现版本和原始/增强对照。规则/Agent初筛过曝、全黑、裁掉目标、接触区变化、颜色语义、闪烁、多相机冲突和数值变化；人重点复核新配方、高风险几何/生成方案及Agent疑点。不能因Agent说好看就批准。官方单帧预览不足，工作台需补首中末帧、关键接触时段、多路相机和强度边界样本。

固定划分、训练预算和评价场景，对照不增强/保守增强/更强增强，使用重复运行或多个seed；以未增强的独立真实样本与闭环成功/失败为准。RAD、DrQ、MimicGen、GenAug/ROSIE的结果只支持其各自设置，不保证G1搬箱收益。详细方法、限制和来源在离线增强专项说明。

## 幻灯片 13（正文 11）当前 28 维数据，腰和腿在哪里？

![当前 28 维数据，腰和腿在哪里？](../../artifacts/report/full_v14/page-13.png)

### 精讲口述

当前G1加Dex3、手追踪这条路线保存双臂双手28维，body为空，标准转换器也不读取body。另一些controller配置确实会记录含腰腿的身体状态，并记录三维移动速度，但这些速度不是每个腿关节的目标。G1原始状态还含保留槽位，不能按数组长度叫自由度。因此要做连续移动，需要把真正下发的移动意图与相应状态同步记下来，不能只把28维补零成43维。

### 扩展讲稿与原始出处

固定teleop_hand_and_arm.py核查：Dex3+hand（报告主线）current_body_state/current_body_action为空，--motion本身不改变该记录分支；可以经R3控制行走，但这个分支的EpisodeWriter没有记R3移动命令。Dex1+controller、BrainCo+controller等另一些分支会记录body：states.body.qpos来自get_current_motor_q，actions.body.qpos却是[vx,vy,vyaw]。body动作字段虽叫qpos，语义实际是速度命令，不是腿部关节目标；且未启用--motion时摇杆数值未必实际发送，不能把“记录的数值”自动当成已执行命令。

G1_29的get_current_motor_q遍历枚举返回35个槽，0–28为29个有效身体关节，29–34为六个保留槽；腰是12–14，腿0–11，臂15–28。严禁把35项称为35个有效关节。主页面只写含保留槽位，详细索引留讲稿。

固定unitree_lerobot标准G1 Dex3/Dex1/Brainco/Inspire配置只拼臂与末端，不取body。即便源JSON有身体状态，也不会自动进入训练。MoveibleLift/Lift/UseWaist等其他专用配置不能当双足G1全身开关。

推荐补充同步字段：实际身体/腰腿状态、基座姿态/速度或里程计（可取得时）、真实下发的底盘速度或导航目标、双腕/手指控制目标、本轮控制模式、任务阶段、负载/接触等对任务重要的上下文。实际需记录哪些由控制/训练契约决定，不是每个字段都能从现有样本推导出来。旧28维示范可支持操作部分或预训练，完整携箱行走还需覆盖新范围并评价。

### 页 A：当前 28 维数据，腰和腿在哪里？

**讲稿建议：**

前面讨论的 28 维，是左右臂各 7 维、左右 Dex3 手各 7 维。按这套 G1_29 + 双 Dex3 的参考配置，身体还有 12 个腿部关节和 3 个腰部关节，总计 43 个自由度。但数据能训练什么，取决于实际记录了什么。当前固定版本的 Dex3 + hand 分支把 body 状态和 body 动作写为空，所以它是一份双臂、双手的操作数据，不是全身搬运数据。[1][2][3]

这里也不能简单说“官方程序完全没有记录身体的能力”。Dex1、外接 Brainco 等部分控制器分支会记录 `get_current_motor_q()` 的结果，同时记录摇杆给出的三维移动速度。对于 G1_29，这个函数遍历 35 个底层槽位，其中 0–28 对应 29 个身体关节，29–34 在这个枚举里标记为未使用；它不是已经整理干净的 29 维关节向量。不同手型、内接夹爪和固件还要核对具体槽位解释。[1][3]

另一个容易误解的地方是：这版原始 JSON 把身体动作仍放在 `actions.body.qpos` 名下，但实际内容是前后速度、左右速度、转向角速度；不能按名字把它解释成髋、膝或踝的角度目标。标准 G1 转换配方又没有读取 body，所以原始包里有这些字段，也不代表导出的 LeRobot 数据会保留下来。[1][2][4]

因此下一步不是补一个“腿部策略名称”。应先确定要学习哪一层动作，再让记录器、转换器和部署接口使用同一份定义。缺失的腰腿命令不能通过改标签、补零或切换 `--policy.type` 产生。

页脚来源：Unitree `--motion` 说明；Isaac Lab v2.3.0 G1 Locomanipulation 官方文档与源码。

**讲稿建议：**

完成“拿起、行走、放下”，并不要求首版模型直接预测每个髋膝关节角。可以让操作策略负责双臂双手，让导航或操作者给出机身移动速度，再由已有的平衡与行走控制生成腿部动作。中间还需要任务阶段控制，决定什么时候可以起步、携带时如何保持抓持、到位后什么时候允许放置。这是建议的首阶段工程路线，不代表当前工作台已经把这些模块联调完成。

宇树的 `--motion` 已经体现了并行控制的思路：手臂命令改发 `rt/arm_sdk`，同时读取 `rt/lowstate`；控制器模式下，摇杆通过 LocoClient 发送 `vx / vy / yaw_rate`。手部追踪模式可以由 R3 控制正常行走。但这不代表当前 Dex3 手追踪记录器保存了 R3 命令，也不代表现有臂手部署脚本已经具有导航、腰部协调和整段任务状态机。[5][6]

更完整的官方例子是 Isaac Lab v2.3.0 的 G1 Locomanipulation 数据生成。它读取匹配的静态操作示范，按抓取、抬起、导航、接近和放置等阶段生成轨迹。高层给出的是机身速度、双腕位姿和手指目标。源码中，上身的 Pink IK 可控制腰部关节；下身调用预训练 Agile 行走策略，最后才得到腿部关节位置目标。因此“模型动作里没有逐个腿关节角”和“机器人没有腿部控制”是两回事。[7][8][9]

这个例子能说明工具与架构已经有公开参考，也提供了数据生成入口；不能用它证明我们的双臂抱箱任务已经完成。现成任务名称是 SteeringWheel，迁到真实箱体时仍要处理双手接触、重量、摩擦、遮挡、桌高、携带姿态和放稳条件，再通过闭环评估确认效果。

| 问题 | 核查结果 | 对管线的影响 |
|---|---|---|
| 43 自由度为什么导出只有 28 维？ | 参考硬件为身体 29 + 双手 14；当前 Dex3/hand 记录 body 空，标准配置仅选双臂双手。 | UI 需展示“实际覆盖的动作部位”，不能只展示本体总 DOF。 |

| body 状态有多少维？ | G1_29 的该读取函数返回 35 个底层槽位；0–28 为身体关节，29–34 在该枚举中未使用。内部夹爪等具体模式还需结合设备解释。 | 保留 raw slot 信息，导出时按已核验有效索引和名称选取，不写“35 DOF”。 |
| body 动作是什么？ | 对上述 controller 记录分支，是三维摇杆移动速度，虽然字段名仍为 qpos。记录分支本身未检查 `args.motion`。 | 还需记录控制模式与命令实际发送状态；没有 motion 时，记录摇杆值不能证明行走命令已执行。 |
| 开 motion 是否就能记录完整搬运？ | 不能。Dex3/hand 中 body 仍空；R3 移动输入也未在此分支记录。 | 要补接移动命令采集。仅有腿部反馈，不能还原当时准确下发的高层命令。 |
| 标准转换会保留 body 吗？ | G1 Dex3/Dex1/Brainco/Inspire 标准配置均只取臂手。 | 移动操作需新增转换配方；不得假定通用输出已包含全身。 |

| 腰部怎么办？ | 当前 28 维策略无独立腰部动作；要通过已验证的姿态/全身控制接口或包含腰的 IK 规划解决。 | 不要臆造一个 LocoClient 腰关节控制参数，也不要默认普通双臂 IK 已包含腰。 |

## 后续实现方案：确定学习层级，再定义数据

### 路线一：分层移动操作，建议首期推进

1. 操作层执行抓取、保持携带姿态与放置；输出可为臂手关节目标或双腕位姿加手部目标，必须匹配实际执行后端。
2. 导航层根据目标桌位、定位与障碍物提供机身速度命令；早期也可由操作者提供，先验证整条采集和控制链。
3. 通过厂商或已验证控制器完成站立、行走和平衡；上身控制与下身控制要协调载荷、姿态和控制权。
4. 任务阶段控制负责抓持确认、起步条件、到达判断、放置条件、失败与人工接管回流。先分段验收，再接成长序列。

建议记录：

| 信号 | 最小内容 | 用途 |
|---|---|---|
| 图像与时间 | 已用相机、帧时间、同步关系 | 保持视觉/状态/动作对应 |
| 实际关节 | 臂手状态；有效的腰腿 q，按需要补 dq | 重建全身实际状态、排查异常 |
| 高层操作目标 | 实际下发的臂手 q 或 EEF pose / 手指目标 | 操作模仿学习目标 |
| 高层移动目标 | vx、vy、yaw_rate；实际使用的姿态/高度目标 | 学习或复现导航与携带动作 |
| 控制上下文 | 模式、控制权、控制器和配置版本、目标是否发送成功 | 确认动作语义，处理接管和无效命令 |
| 机身状态 | IMU 姿态/角速度；可得的定位、速度估计 | 平衡、移动操作观测与诊断 |
| 任务上下文 | 桌位、阶段、物体/载荷、成功失败与接管 | 训练条件、筛选、评估 |

触觉、足端接触、力/力矩等字段在实际具备传感器或可靠估计时追加；未测量的内容不要填成“真实观测”。基座速度的单位应为 m/s，转向为 rad/s，关节 q 为 rad；坐标系、绝对/相对动作和目标时间必须写入契约。

### 路线二：直接学习全身或全身目标，作为后续独立模块

可选择学习全身关节目标、人体重定向目标、全身末端目标或 latent skill。这些方案不是同一种 action。需要匹配的全身遥操作/重定向或仿真轨迹生成、全身控制器、全身观测、训练后端和部署约束。

若目标是 G1_29 + Dex3 的逐关节控制，可从 29 个有效身体关节 + 14 个手部关节定义状态，另行明确动作是否同样是 43 维关节目标；若采用速度/末端/技能接口，动作维度可能完全不同。关节数相同也不证明可以直接执行，必须确认顺序、限位、动作定义和控制频率。

## 幻灯片 14（正文 12）连续搬箱：操作策略与行走控制怎样协作

![连续搬箱：操作策略与行走控制怎样协作](../../artifacts/report/full_v14/page-14.png)

### 精讲口述

连续搬箱需要抓取、抱持移动和放置的阶段协同。上层可以给双腕、手指和机身移动目标，下层由IK和既有行走控制负责执行与平衡。现有遥操作的motion模式就提供了手臂与运控并行的入口，但R3人工行走不等于自主导航。Isaac Lab也有这种分层locomanipulation工具例子，包含移动目标和双手目标；其现成SteeringWheel任务仍需适配和验证搬箱，不能说已经有即拿即用的抱箱模型。

### 扩展讲稿与原始出处

G1_29手臂控制在--motion时从rt/lowcmd切到rt/arm_sdk，以与既有运动控制协作。controller分支通过LocoClient.Move(vx,vy,vyaw)发送移动速度；hand分支可用R3另控行走。这是手臂/运控并行，不是自动生成连续搬箱策略或完整记录的开关。

建议的工程路线：任务/导航层管理桌A取箱、抱持移动、桌B放置的目标与阶段条件；操作/协调策略给双腕/手指目标及移动意图，低层控制器根据实际反馈维持身体运动。腰部由具体控制配置协调，例如Isaac Lab例子中的上身IK包含腰关节，腿由下层行走策略产生目标。不要把现有28维模型直接接到全身电机，也不能只并行播放互不协调的手臂和行走轨迹。

权威现成例子：Isaac Lab v2.3.0的scripts/imitation_learning/locomanipulation_sdg/generate_data.py，任务Isaac-G1-SteeringWheel-Locomanipulation。实际CLI参数是--task、--dataset、--output_file、--lift_step、--navigate_step、--num_runs，文档中的output_file_name不是源码参数。需要配套manipulation HDF5与场景，不接受任意宇树JSON。

生成逻辑用build_action_vector组织base_velocity_target、左右手pose与手指关节位置；环境用含腰的上身IK和Agile下身行走策略执行，不能说高层GR00T必然直接输出每个腿关节。若选择端到端全身关节策略，则要另准备匹配观察/目标、运动/接触/负载覆盖及控制器，并单独验证稳定性与任务成功。

  - 双臂 14 + 双手 14 → 标准转换配置导出 28 维 state / action。
  - 该采集分支的 `states.body`、`actions.body` 为空，腰腿没有进入这份训练数据。[1][2]
- **其他分支：可以出现身体状态与移动命令**
  - 部分“控制器追踪 + 夹爪/手”分支记录身体电机状态和 `vx / vy / yaw_rate`。
  - 状态与命令含义不同；移动速度命令不是腿关节目标角。[1][3]
- **转换仍需补齐**
  - 标准 `Unitree_G1_Dex3` 等配置只选臂和手，忽略 `body`。
  - 换训练策略不会自动补出腰腿；需要补记录，并增加对应的数据配方与执行接口。[2][4]

页脚来源：官方 `xr_teleoperate` 采集分支与 `unitree_lerobot` 的 G1 配置；详细链接放讲稿。

**讲稿建议：**

前面讨论的 28 维，是左右臂各 7 维、左右 Dex3 手各 7 维。按这套 G1_29 + 双 Dex3 的参考配置，身体还有 12 个腿部关节和 3 个腰部关节，总计 43 个自由度。但数据能训练什么，取决于实际记录了什么。当前固定版本的 Dex3 + hand 分支把 body 状态和 body 动作写为空，所以它是一份双臂、双手的操作数据，不是全身搬运数据。[1][2][3]

这里也不能简单说“官方程序完全没有记录身体的能力”。Dex1、外接 Brainco 等部分控制器分支会记录 `get_current_motor_q()` 的结果，同时记录摇杆给出的三维移动速度。对于 G1_29，这个函数遍历 35 个底层槽位，其中 0–28 对应 29 个身体关节，29–34 在这个枚举里标记为未使用；它不是已经整理干净的 29 维关节向量。不同手型、内接夹爪和固件还要核对具体槽位解释。[1][3]

另一个容易误解的地方是：这版原始 JSON 把身体动作仍放在 `actions.body.qpos` 名下，但实际内容是前后速度、左右速度、转向角速度；不能按名字把它解释成髋、膝或踝的角度目标。标准 G1 转换配方又没有读取 body，所以原始包里有这些字段，也不代表导出的 LeRobot 数据会保留下来。[1][2][4]

因此下一步不是补一个“腿部策略名称”。应先确定要学习哪一层动作，再让记录器、转换器和部署接口使用同一份定义。缺失的腰腿命令不能通过改标签、补零或切换 `--policy.type` 产生。

**讲稿建议：**

完成“拿起、行走、放下”，并不要求首版模型直接预测每个髋膝关节角。可以让操作策略负责双臂双手，让导航或操作者给出机身移动速度，再由已有的平衡与行走控制生成腿部动作。中间还需要任务阶段控制，决定什么时候可以起步、携带时如何保持抓持、到位后什么时候允许放置。这是建议的首阶段工程路线，不代表当前工作台已经把这些模块联调完成。

宇树的 `--motion` 已经体现了并行控制的思路：手臂命令改发 `rt/arm_sdk`，同时读取 `rt/lowstate`；控制器模式下，摇杆通过 LocoClient 发送 `vx / vy / yaw_rate`。手部追踪模式可以由 R3 控制正常行走。但这不代表当前 Dex3 手追踪记录器保存了 R3 命令，也不代表现有臂手部署脚本已经具有导航、腰部协调和整段任务状态机。[5][6]

更完整的官方例子是 Isaac Lab v2.3.0 的 G1 Locomanipulation 数据生成。它读取匹配的静态操作示范，按抓取、抬起、导航、接近和放置等阶段生成轨迹。高层给出的是机身速度、双腕位姿和手指目标。源码中，上身的 Pink IK 可控制腰部关节；下身调用预训练 Agile 行走策略，最后才得到腿部关节位置目标。因此“模型动作里没有逐个腿关节角”和“机器人没有腿部控制”是两回事。[7][8][9]

这个例子能说明工具与架构已经有公开参考，也提供了数据生成入口；不能用它证明我们的双臂抱箱任务已经完成。现成任务名称是 SteeringWheel，迁到真实箱体时仍要处理双手接触、重量、摩擦、遮挡、桌高、携带姿态和放稳条件，再通过闭环评估确认效果。

## 逐项事实与边界

| 问题 | 核查结果 | 对管线的影响 |
|---|---|---|
| 43 自由度为什么导出只有 28 维？ | 参考硬件为身体 29 + 双手 14；当前 Dex3/hand 记录 body 空，标准配置仅选双臂双手。 | UI 需展示“实际覆盖的动作部位”，不能只展示本体总 DOF。 |
| 现有采集是否绝对不支持腰腿状态？ | 并非如此：Dex1/Dex1_internal 的 controller 分支及 Brainco/controller 分支会调用全电机状态读取；但当前 Dex3/hand 不这样做。 | 配方必须包含本体、末端、输入模式与记录版本，不能只看机器人名字。 |
| body 状态有多少维？ | G1_29 的该读取函数返回 35 个底层槽位；0–28 为身体关节，29–34 在该枚举中未使用。内部夹爪等具体模式还需结合设备解释。 | 保留 raw slot 信息，导出时按已核验有效索引和名称选取，不写“35 DOF”。 |
| body 动作是什么？ | 对上述 controller 记录分支，是三维摇杆移动速度，虽然字段名仍为 qpos。记录分支本身未检查 `args.motion`。 | 还需记录控制模式与命令实际发送状态；没有 motion 时，记录摇杆值不能证明行走命令已执行。 |
| 开 motion 是否就能记录完整搬运？ | 不能。Dex3/hand 中 body 仍空；R3 移动输入也未在此分支记录。 | 要补接移动命令采集。仅有腿部反馈，不能还原当时准确下发的高层命令。 |
| 标准转换会保留 body 吗？ | G1 Dex3/Dex1/Brainco/Inspire 标准配置均只取臂手。 | 移动操作需新增转换配方；不得假定通用输出已包含全身。 |
| 选带 Waist 的 robot_type 即可？ | 现有 MoveibleLift/Lift 配置读取 `waist.qpos`、`torso.height/qvel`、`chassis.qvel` 等特定输入；不是双足全身导出开关。 | 不能把另一类硬件输入配方当作 G1 双足腿数据映射。 |
| 现有转换器能否随意拼接速度动作？ | 固定版本对 observation.state/action 都使用 len(motors)；身体观测和机身速度目标可能维度、单位都不同。 | 新后端必须分别定义 observation/action 的 feature、维度、顺序和单位，必要时扩展导出器。 |
| motion 模式怎样控制腿？ | 上层发机身速度，底层已有运控生成腿动作；臂手命令走 arm_sdk。 | 导出高层速度动作并复用运控是一种可行设计；不必一开始直接学腿关节目标。 |
| 腰部怎么办？ | 当前 28 维策略无独立腰部动作；要通过已验证的姿态/全身控制接口或包含腰的 IK 规划解决。 | 不要臆造一个 LocoClient 腰关节控制参数，也不要默认普通双臂 IK 已包含腰。 |

补充源：`--motion` 仅支持官方描述的 Regular 模式；内部接线 Dex1 同时使用 motion 在固定 README 中明确为不支持。不能因代码里存在记录分支，就宣布某种硬件控制组合已获验证。

## 后续实现方案：确定学习层级，再定义数据

### 路线一：分层移动操作，建议首期推进

1. 操作层执行抓取、保持携带姿态与放置；输出可为臂手关节目标或双腕位姿加手部目标，必须匹配实际执行后端。
2. 导航层根据目标桌位、定位与障碍物提供机身速度命令；早期也可由操作者提供，先验证整条采集和控制链。
3. 通过厂商或已验证控制器完成站立、行走和平衡；上身控制与下身控制要协调载荷、姿态和控制权。
4. 任务阶段控制负责抓持确认、起步条件、到达判断、放置条件、失败与人工接管回流。先分段验收，再接成长序列。

建议记录：

| 信号 | 最小内容 | 用途 |
|---|---|---|
| 图像与时间 | 已用相机、帧时间、同步关系 | 保持视觉/状态/动作对应 |
| 实际关节 | 臂手状态；有效的腰腿 q，按需要补 dq | 重建全身实际状态、排查异常 |
| 高层操作目标 | 实际下发的臂手 q 或 EEF pose / 手指目标 | 操作模仿学习目标 |
| 高层移动目标 | vx、vy、yaw_rate；实际使用的姿态/高度目标 | 学习或复现导航与携带动作 |
| 控制上下文 | 模式、控制权、控制器和配置版本、目标是否发送成功 | 确认动作语义，处理接管和无效命令 |
| 机身状态 | IMU 姿态/角速度；可得的定位、速度估计 | 平衡、移动操作观测与诊断 |
| 任务上下文 | 桌位、阶段、物体/载荷、成功失败与接管 | 训练条件、筛选、评估 |

触觉、足端接触、力/力矩等字段在实际具备传感器或可靠估计时追加；未测量的内容不要填成“真实观测”。基座速度的单位应为 m/s，转向为 rad/s，关节 q 为 rad；坐标系、绝对/相对动作和目标时间必须写入契约。

### 路线二：直接学习全身或全身目标，作为后续独立模块

可选择学习全身关节目标、人体重定向目标、全身末端目标或 latent skill。这些方案不是同一种 action。需要匹配的全身遥操作/重定向或仿真轨迹生成、全身控制器、全身观测、训练后端和部署约束。

若目标是 G1_29 + Dex3 的逐关节控制，可从 29 个有效身体关节 + 14 个手部关节定义状态，另行明确动作是否同样是 43 维关节目标；若采用速度/末端/技能接口，动作维度可能完全不同。关节数相同也不证明可以直接执行，必须确认顺序、限位、动作定义和控制频率。

## 幻灯片 15（正文 13）模型怎样从示范中学习

![模型怎样从示范中学习](../../artifacts/report/full_v14/page-15.png)

### 精讲口述

以行为克隆为例，训练器读取示范中的观察，让策略预测目标动作或动作序列，再比较预测与示范来更新参数。图像、状态和语言是否使用，按具体配方选择；不同策略的结构和训练目标也有差别。[1][2]

启动时要固定数据字段、策略与时间窗口，以及批量大小、步数、学习率、随机种子和运行设备。训练、验证和测试按完整回合隔离，同源增强跟随母回合。结束后一起保存模型、预处理、统计量和配置，再进入闭环评价，而不只看训练损失。[2][3]

### 扩展讲稿与原始出处

这一页以行为克隆解释示范怎样变成模型。训练器读取示范中的观察，例如图像、实际关节状态和按配方需要的任务文本，让策略预测目标动作或一段动作序列，再按该策略的训练目标比较预测与示范，更新参数。ACT、Diffusion 等实现的具体结构与损失不同，但都需要把训练样本的含义说清楚。[1][2]

真正启动训练时，需要固定三类配置：用哪份数据、哪些相机与状态动作字段；采用哪种策略、观察和动作窗口；以及 batch size、训练步数、学习率、随机种子和运行设备等训练参数。ACT 还会涉及 chunk_size、n_action_steps 等策略参数，不能仅修改模型名称。[2][3]

数据划分也属于配方。这里建议按完整回合隔离训练、验证与测试，同源增强数据跟随母回合，避免相邻帧泄漏。训练结束要一起保存 checkpoint、预处理与归一化统计、配置和数据指纹。下一页再看：模型进入环境后究竟能否完成任务。

### 精讲口述

闭环评价让环境提供当前图像与状态，策略产生动作，执行后再读取新的反馈。这样才能观察误差累积和任务完成情况。宇树提供特定组合的仿真任务，但桌 A 到桌 B 的自定义搬箱场景仍需配置。[1][2]

### 扩展讲稿与原始出处

评估时要让模型真正进入闭环：环境给出当前图像和状态，策略据此产生动作，控制器执行后，环境再返回新的反馈。这样才能观察误差是否累积、抓持是否稳定，以及任务是否完成。宇树提供特定本体、手型和任务的仿真场景及策略评估入口，但自定义的桌 A 到桌 B 抱箱任务仍要配置场景和成功判定。[1][2]

这与两类常见演示要分开。记录回放使用已经保存的动作；离线预测的输入仍来自记录数据；闭环策略的下一步输入来自环境反馈。三者都可用于检查，但回答的问题不同。

对于搬箱，我们会先约定初始条件、是否到达桌 B、箱子是否放稳，以及掉落、超时和人工接管怎样记录。报告保留所有已开始的尝试与中止原因，再计算约定指标。当前固定骨盆的 G1 数值实验没有完整物体任务，也没有学习行走，因此不能用它宣称搬箱成功。

一、外部数据可能交付到哪一步

第一类是原始传感与日志。文件可包含相机原视频、设备日志或按话题记录的传感器和控制消息。DROID 官方资料同时提供原始数据和已整理的训练表示，说明“同一个数据集名字”也可能对应不同交付层级。[1] 我们先核对交付结构、回合边界及已有索引；必要时解包、解码或分段，再根据已有时间与标定信息核对各路信号。原始交付物可能已经按回合组织，不要求一律重切。必要的对齐或标定处理要有依据；原材料缺失时，应向供应方补要或补采，不能靠脚本编造真值。准备后接回原始记录和质检。

第二类是已经整理好的轨迹。它可能已经有 episode、图像、state、action 与任务文字，但来源机器人的关节顺序、单位、参考坐标、绝对/增量动作、末端/关节表示或相机名称仍可能与我们不同。此时先做来源 schema 到目标契约的语义适配，接回质检、适配和转换。openpi 的 RepackTransform、data transforms 与模型变换展示了数据键重组和机器人/模型相关适配的分工，而不是仅改变磁盘文件后缀。[3]

第三类是已有训练格式的数据。比如一份 LeRobot 数据，存储组织已经能被对应版本的读取器识别，但仍要核对实际目标相机、状态/动作维度和含义、时间窗、归一化与任务文本，以及目标模型配置。[2][3] 在来源说明、抽样核验和相应质量范围明确后，用目标读取器做实际 batch 读取与试运行，并核对训练/验证/测试划分及归一化统计量。匹配时可直接复用该训练输入，跳过重复解包和无必要的格式转换；这不等于已经证明任务效果，也不意味着可以跳过适用性或质量检查。

不能预先断言外部数据“多数能直接训练”。这取决于供应商交付层级和我们选定的有限任务、本体与训练配方。“已有训练格式”和“已经适合我们的配方”应分开记录。

二、为什么还会有另一条处理路径

若源本体或动作语义不同，可能需要运动学重定向、动作表达变换或专项算法验证；缺少关键视角、时间/标定依据、有效语言标注或腿腰/移动目标，则可能需要补材料、补标或补采。单纯把 HDF5 改存 Parquet、把一个字段改名，不会自动解决这些缺口。图底部把它列为额外分支，它可叠加到前面任何一条路径，不是第四种互斥数据类型。

这些额外作业的结果还要重新进入语义和质量核验，再确定最终接入位置。数据增强仍按目标配方和标签有效性决定，不能要求每份外部数据都先增强一遍。

三、工作台后续怎样组织

导入时登记来源、版本、交付范围、源本体、任务、模态、动作表达和已处理阶段。任务创建者再选择目标本体和有限训练配方，平台给出“直接复用、规则适配、专项适配、补材料/补采”的可解释建议，显示依据、缺口与待执行作业。用户按阶段按钮执行，必要时选择自动串联，留下输入、配置、产物和核验结果。

这套接入方案不要求现在支持所有厂商和所有模型。首期固定单人、单 G1 与有限配方，新增本体或方法时扩展相应读取、适配或采集后端。下一页采购需求就要把交付层级、适配范围和缺失信息写清楚；供应方与我们分别负责哪些准备，不能只约定一个数据文件格式。

## 幻灯片 21（正文 18）数据采购：甲方怎样提需求

![数据采购：甲方怎样提需求](../../artifacts/report/full_v14/page-21.png)

### 精讲口述

采购前先把任务和目标本体固定下来。搬箱需要哪些阶段、什么手型和相机、哪些状态与动作，要写成能够对照样本的需求。数量也不只看文件大小，而要约定有效回合、时长、场景和成功失败覆盖。[1][2]

已有数据先拿清单和代表样本，对照缺项；委托新采先试采，修正规格后再分批交付。原始包、说明、标定、转换责任、整改方式及允许用途一起说清。这是我们的工程需求单，具体数量与门槛要围绕任务约定，不是统一采购标准。

### 扩展讲稿与原始出处

采购时先固定任务和目标本体，再讨论买什么。以搬箱为例，要说清需要取箱、抱持、负载移动和放置中的哪些阶段，并说明手型、相机、状态和动作怎样定义。数据说明框架和 Dataset Cards 提醒我们记录组成、采集方法、缺失与用途，但机器人专属需求仍要由本项目补全。[1][2]

数量不能只看文件大小。我们要一起看不重复的有效回合、时长、物体和场景覆盖，也要记录成功、失败和中止的分布。重复增强得到的数据量与原创示范量应分开说明。

如果供应商已经有数据，先要清单和代表样本，对照缺口。如果需要委托新采，先试采，修订规格后再分批交付。交付哪些原始包、说明与标定，谁负责转换和整改，数据及模型产物允许怎样使用，也应一起明确。这张表是项目的工程需求单，具体数量和门槛需要双方结合任务约定。

## 幻灯片 22（正文 19）数据采购：用样本验证适配性

![数据采购：用样本验证适配性](../../artifacts/report/full_v14/page-22.png)

### 精讲口述

验证采购数据，先取得清单、字段说明、来源和已知缺项，再按主要任务场景选择代表样本，并加入随机样本。之后预览图像、状态和动作，核对时间关系，按明确规则转换，用真正采用的训练读取器加载。[1][2]

已知单位换算或字段重排可以模板化；缺少关键视角、移动指令或本体对应关系，则需补材料、补采或专项适配。最终留下直接满足、规则可转换、需额外适配、需补采的结论。读取通过、训练能跑和任务有效，要分别记录。

### 扩展讲稿与原始出处

供应商说能用，或者转换一下就能用，我们要把这句话变成可以复查的证据。先拿清单、schema、来源说明和已知缺项，按主要任务与场景分层选择样本，同时加入随机样本，避免只看几段成功视频。

然后预览图像、状态和动作，检查时间关系，按明确映射执行必要转换，再用我们真正采用的读取器和训练配置加载。转换脚本只能处理它已有规则覆盖的字段，无法凭空产生缺失信号。[1][2]

例如，已知单位换算或字段重排可以做成重复执行的模板；缺少负载移动指令、关键视角或本体对应关系，就需要补材料、补采或者单独研究。最后记录直接满足、规则可转换、需要额外适配、需要补采四种结论，以及各自的责任和证据。读取通过、小规模训练能运行，与在独立条件下完成任务是三种不同结论，采购范围应据此确认，后续批次再沿用约定的检查规则。

## 幻灯片 23（正文 20）现有流程中的交接成本

![现有流程中的交接成本](../../artifacts/report/full_v14/page-23.png)

### 精讲口述

前半部分介绍的工具已经能完成很多单项工作，有些也已有图形界面。真正需要我们梳理的是交接：采集时怎样判断多个设备真的准备好了，外部数据怎样避免反复查找，转换后怎样知道当前配方能用，以及失败后怎样继续。因此平台的价值要落在减少重复配置、解释适配条件和恢复失败步骤上，不能只说把命令行放进网页。这里的不便是对工具流程和我们试用的分析，目前还没有做用户耗时统计。

### 扩展讲稿与原始出处

这一页是背景向方案的转折。获取环节既包括PC2、Host、Vision Pro等多个设备的准备，也包括外部数据的来源、版本和持有范围。处理环节要核对动作、相机、时间与任务质量，格式可读取只是其中一项。使用环节还有训练配方、执行环境、闭环场景与部署接口。迭代环节需要找回一次实验的输入和产物，并保留成功步骤。

现有生态已经提供不少能力。LeRobot官方LeLab指南描述了设备配置、遥操作、采集、训练和推理图形流程，同时注明当前仅支持SO-ARM101。这证明图形界面本身不是独占价值。我们是否需要自研每一块，应先比较可复用组件与G1、外部资产、采购和恢复流程的差异。不能把工程分析写成整个行业都缺某功能，也不引用未经实测的节省百分比。

## 幻灯片 24（正文 21）理想方案：围绕任务组织完整流程

![理想方案：围绕任务组织完整流程](../../artifacts/report/full_v14/page-24.png)

### 精讲口述

使用者先带着任务和本轮范围进入平台。数据有两类入口：自己用真机或仿真采集，或者登记公开和采购来源。两条路径都进入可复用的资产与回合视图，按当前本体、用途和配方检查，必要时适配或增强，然后实际训练、闭环评价和受限部署。整条流程共享执行记录，评价发现的问题再形成补采或重标待办。每阶段都有独立操作，条件明确后可选择串联，不能跳过头显连接和现场确认。

### 扩展讲稿

这张图表达未来完整方案，不是当前完成度。任务项目同时保存总目标与本轮验收范围，例如总目标是从桌A搬到桌B，本轮先做受限双臂抓放。源数据任务与目标任务分别保存。

资产库保留来源、版本和实际持有范围，数据视图表达这次选择哪些回合、哪些切段与划分。公开数据、采购数据可能处于不同处理阶段，因此按缺项接入，不强制重复执行已经完成且验证过的步骤。

检查与适配之后还要由目标后端实际加载样本。训练完成只产生模型，不代表任务成功；闭环评价与受限实机验证各有证据。失败应显示在哪个设备、哪个阶段，成功产物可复用。反馈不只是留日志，还应变成可执行的数据或配置改进待办。

首期单人单机器人、少量已支持配方。平台复用厂商与开源后端，不承担实时控制算法本身，也不承诺跨本体数据和模型自动迁移。

## 幻灯片 25（正文 22）选数据时，先回答当前组合能做什么

![选数据时，先回答当前组合能做什么](../../artifacts/report/full_v14/page-25.png)

### 精讲口述

同一份数据能不能用，需要结合当前任务、用途、本体和配方。标签用于找候选，随后核对任务覆盖、观察动作、时序质量、本体控制、读取器和使用条件。我们把来源条目、实际持有的数据和本次回合视图分开，既允许先登记或先取样，也方便以后直接复用。结果不简单写通用或者专用，而是说明条件满足、已有适配可处理、缺材料，还是需要新适配。

### 扩展讲稿

用户流程是确定目标、取得候选、选回合视图、看差异、准备输入、实际使用。来源网址可以先登记，下载时固定版本和范围；本地硬盘交付保留批次清单。不要把登记数量算成已持有数据量，也不要把样本试读说成整库完整。

任务相关性只是第一层。还需核对观察与动作定义，包括实际反馈state和下发目标action、单位、参考系、控制频率、时间关系、相机以及目标控制范围。配方与用途也会影响要求，预训练候选不等于能直接用于目标机器人闭环。许可或交付用途条件不明应保留待确认。

适用性绑定数据版本与视图、目标本体配置、训练配方和适配配置。改关键条件时复查受影响项，不能给资产一个永久可训练标记。已有训练格式若已被匹配读取器验收，可复用而不再强制导出。资料缺失时允许归档和预览，但阻断相应训练。

以上是本项目选数与交互设计，尚未实现自动适用性判断。

## 幻灯片 26（正文 23）交互设计：当前条件与下一步放在首屏

![交互设计：当前条件与下一步放在首屏](../../artifacts/report/full_v14/page-26.png)

### 精讲口述

这是独立的方案原型，不是已经接通硬件的界面。左边按日常任务导航，中间先显示当前的数据、本体和配方，再给阶段进度与阻断原因。用户不用先理解底层脚本，只需知道为什么当前不能训练，以及下一步该补什么。采集、资产、准备数据、实验和记录都能进入细节；平时只突出一个主操作。失败保留输入和成功步骤，系统选择目录等常见动作沿用原生习惯。

### 扩展讲稿

原型可以点击体验，但所有设备、数据和实验状态都是示例，不连接机器人、不下载、不训练，也不改正式工作区。它用于评审流程和文案。

当前任务作为主入口，资产可跨任务引用。整理者负责来源登记、样本获取、分类和字段确认，训练使用者负责回合视图、配方与实验，同一人可承担两种角色，不因此引入多用户权限系统。

采集页按只读检查、服务准备、等待头显、启用跟随、录制、保存、完成组织。保存失败只恢复保存步骤，未完成回合隔离。外部资产页区分仅登记、样本、部分与完整范围，原始任务不被目标任务覆盖。准备数据页先显示差异和已支持处置，再检查目标后端读取。换配方会让相应读取结论需复查，保留原件和可复用映射。

专业设计检查采用状态可见、减少记忆、错误预防和可恢复等原则。尚未进行真实用户测试，后续需要邀请代表用户完成采集、选数和恢复任务。

## 幻灯片 27（正文 24）有限支持清单，按需增加适配后端

![有限支持清单，按需增加适配后端](../../artifacts/report/full_v14/page-27.png)

### 精讲口述

我们的实际机器人和模型数量很少，所以先完成一个G1配置和一个训练配方。共享的是任务、资产、回合视图、作业和结果。换下载来源增加获取适配，换格式增加读取和转换，换策略增加配方及预处理，换本体还可能影响遥操作、控制、相机和部署。页面按已接入能力开放操作。能连接新机器人与旧数据、旧模型能否迁移，是两项独立验收。

### 扩展讲稿与原始出处

采集接口应封装准备/检查、观察预览、启用遥操作、开始录制、结束并保存和释放本次资源等用户意图。底层实现可以使用厂家SDK、IPC或受控执行器，但需返回真实状态和完成产物，不能只有启动命令。

Unitree当前工具提供特定设备的控制和记录能力，LeRobot的Robot接口体现标准观察和动作接口的思路。它们是可复用依据，不表示本项目已经适配其他厂商。智元、银河通用、机械臂和自研机构按实际采购计划接入，取得SDK、控制语义、传感器与记录条件后逐项验收。

不先实现所有本体乘所有策略的组合。新增来源可能只改来源适配，新增策略可能复用数据容器但仍需配方读取与归一化配置，换本体可能需要新的动作映射、重定向、新采数据和新的评价环境。

跨平台约束分两层：工作台管理服务支持Mac、Windows、Linux；厂商Host、PC2和训练仿真环境按各自实际支持系统运行。远程路径明确属于哪台执行机，不能用本机目录选择器冒充远程选择。

## 幻灯片 28（正文 25）从基础原型到完整管线，分四阶段交付

![从基础原型到完整管线，分四阶段交付](../../artifacts/report/full_v14/page-28.png)

### 精讲口述

当前v0.1.2只完成本地导入、结构检查、自有JSONL导出和记录，是基础原型。后续第一阶段补采集与入库，外部来源基础整理同步开展；第二阶段把处理、固定配方训练和匹配场景仿真接通；第三阶段完成受限部署和失败样本回流，这时才叫第一个完整G1管线；第四阶段按需求增加来源、配方和本体。每一阶段都有可用结果与验收，不用把所有厂商、模型一起做完才交付。

### 扩展讲稿

沿用需求的M0至M4编号：M0是接口盘点与基础原型，当前只完成其一部分，不能说真机采集已有。M1包含设备档案、只读预检、Host桥接、服务编排、XR待办、录制与保存完成事件、回合预览以及外部来源登记和基础编辑。没有硬件也可先开发状态机、模拟适配器、断连恢复和完成回合入库。

M2可拆为M2a来源/视图/检查，M2b官方格式与训练读取，M2c一个训练后端和匹配任务闭环。先选择一个配方，增强按需接入。M3绑定权重、预处理、统计和动作接口，现场验证受限范围并回收失败样本。完整抱箱行走需要额外数据和控制/场景验证，不能沿用双臂抓放结果直接宣称完成。M4才逐项扩展具体组合。

外部数据从M1开始登记与样本整理，M2补有限来源下载/视图复用，不是推迟到M4才考虑。工作包依赖和开发优先级已在产品文档中拆分。排期还取决于到货设备、SDK、环境和实际开发投入，本页不编造完成日期。

## 幻灯片 29（正文 26）用真实任务验收平台价值

![用真实任务验收平台价值](../../artifacts/report/full_v14/page-29.png)

### 精讲口述

平台是否好用，要让使用者完成具体事情。初始化后重复三次采集会话，检查是否还需要手工启动已接入服务；再让同事找回外部样本，解释缺项并建立回合视图；注入保存或转换失败，看能否从失败处继续；最后从评价结果追溯数据、配置和模型。效率先测旧流程基线，策略效果按独立任务判据评价。当前都属于拟验收目标，还没有实测节省比例。

### 扩展讲稿

第一类验收是重复使用：3次会话，每次至少10回合，可靠区分录制、保存、完成和异常，不把进程存活当成业务完成。第二类是可发现性和可解释性：建议5名有基础的同事，至少4名能在无口头提示下找回目标样本、建立视图并说明训练阻断原因。记录用时、求助和误操作，先测基线再确定优化目标。

第三类是失败恢复：相机中断、连接丢失、磁盘不足、保存失败、转换worker退出均定位到设备/阶段，保留输入和成功产物，未完成输出不进入下游。第四类是实验可追溯：从一次闭环评价找到数据视图、划分、增强/转换、统计、配方、模型、场景、日志和视频。

界面流畅、管线运行成功与策略任务成功分开记录。首轮不要求训练立即达到完整搬箱成功率，但必须保存真实评价与失败证据。下一轮优先开发真机采集软件链路，同时修正现有表单语义和状态反馈，再接第一个可训练后端。
