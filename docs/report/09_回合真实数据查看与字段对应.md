# 原始回合数据查看与字段对应

## 精讲口述

这一页展示宇树官方可视化脚本附带的原始回放测试样本，还没有转换为 LeRobot。一个回合包含 data.json 和 colors 图片目录。可以直接打开本地原始文件，也可以通过官方入口下载完整测试包。[1][2]

右边两个数都来自 episode_0006 第一帧的左肩俯仰：states 是实际关节反馈，actions 是目标关节位置。原始 JSON 还保存图像路径和任务文本。样本是旧格式，任务与设备配置需要核对，不能直接当作本次搬箱数据；当前采集代码中的目标在下游还可能经过限幅。[3][4]

## 扩展讲稿

这一页只讲转换前的原始格式。示例来自宇树官方 xr_teleoperate 可视化脚本附带的 rerun_testdata.zip，已直接下载原 ZIP 并提取 episode_0006。data.json 和 JPG 均保留原始字节，没有从 LeRobot 反向导出，也没有人工编造数值。[1][2]

一、原始入口与本地打开方法

官方固定版本 rerun_visualizer.py 的 __main__ 示例在约 192–206 行设置下载链接，再用 gdown 下载 ZIP 并解压到 testdata；读取器直接按 episode_XXXX/data.json 读取并关联图片。这证明这个入口对应原始回合结构。[1]

PPT 页上“浏览原始 JSON 与图像”指向 resources/raw_episode.html，可在浏览器离线按帧查看 JSON 和两路原图；“打开原始 data.json”指向 resources/raw/episode_0006/data.json。链接均相对于 PPT 所在目录。换到 Windows 时，完整解压演示包并保持 演示 PPT 与 resources 的相对位置，无需修改成本机绝对路径。“下载官方原始样例包”仍指向官方 Google Drive，作为联网来源入口。完整原始 ZIP、回合、图片、来源记录和讲稿均随演示包携带，start.html 提供离线资料总入口。

原始目录（本机已解压的完整 episode_0006）：
```text
episode_0006/
  data.json
  colors/
    000000_color_0.jpg
    000000_color_1.jpg
    ...
    000166_color_0.jpg
    000166_color_1.jpg
  depths/
  audios/
```

实际核对：data 中共 167 条记录，idx 从 0 到 166，每条两路 JPG，共 334 张；图像是 640×480，全部被引用图片均可找到。空的 depths/audios 目录或元数据声明不等于实际采集到了深度和音频。ZIP 内另有 episode_0008，其主 data.json 为 375 帧；new_data.json 是另一个 365 帧文件，不能混淆。页面只使用 episode_0006。[1][2]

二、同一条原始记录怎样看

顶层 info 保存格式与采集配置等元信息，text 保存任务说明，data 是顺序记录列表。下面从真实 JSON 抽取少量字段，保留被展示字段的完整原值，省略其他身体部位和字段；完整文件可直接打开。

```json
{
  "text": {
    "goal": "Pick up the red cup on the table."
  },
  "data": [
    {
      "idx": 0,
      "colors": {
        "color_0": "colors/000000_color_0.jpg",
        "color_1": "colors/000000_color_1.jpg"
      },
      "states": {
        "left_arm": {
          "qpos": [
            -0.3336954116821289,
            0.10036659240722656,
            0.157912015914917,
            0.3875539302825928,
            -0.24062922596931458,
            -0.3605555295944214,
            -0.33762064576148987
          ]
        }
      },
      "actions": {
        "left_arm": {
          "qpos": [
            -0.3122416753494884,
            0.10507703745573826,
            0.1530567837350236,
            0.3759131536366903,
            -0.23483478321041373,
            -0.36428431290579855,
            -0.33921337998788437
          ]
        }
      }
    }
  ]
}
```

- 图像：data[0].colors.color_0 是 colors/000000_color_0.jpg，相对路径以该 episode 目录为基准。页上小图就是这个原始文件。color_0 / color_1 是流标识，该包没有给出足够信息把它们命名为左右腕相机；两张首帧视觉近似头部双目，不据此确认硬件配置。
- 实际状态：data[0].states.left_arm.qpos[0] 为 -0.3336954116821289；info.joint_names.left_arm[0] 写作 kLeftShoulderPitch，页面对应“左肩俯仰”，四舍五入显示 -0.333695。
- 目标动作：data[0].actions.left_arm.qpos[0] 为 -0.3122416753494884，页面显示 -0.312242。它与实际反馈属于不同物理含义，不表示下一帧反馈一定等于这个目标。
- 任务信息：text.goal 原值是 Pick up the red cup on the table.；text.desc 和 text.steps 另有描述。它们是随回合保存的文字，不能因为存在这段文本就断言机器人实际完成了任务。
- 顺序：data[t].idx 表示记录序号。此样本没有逐条硬件时间戳，info.image.fps=30 是元数据声明，不能因此证明各流严格同步。

三、实际关节反馈与控制目标

用当前报告参考的固定采集代码解释语义：主程序读取 current_lr_arm_q 作为 states 的手臂关节反馈，IK 解算得到 sol_q 并交给控制器，记录 actions 的手臂目标来自 sol_q。真机发布线程还可能按速度约束限幅后再写入 motor_cmd.q，因此“记录的控制目标”和“最终电机命令报文”应分别说明。[3][4]

这是对当前参考代码的语义核查，不证明这个历史样本由当前固定版本采集。旧样本没有提供完整生产提交、明确 robot_type 或完整硬件清单。正式复现仍需核对采集版本、单位、关节顺序、手型、标定和控制模式。qpos 是关节位置表达；空 qvel / torque 列不能当作已取得的速度或力矩。[3][4][5]

四、旧原始样本的明确边界

该包双臂各 7 维、双手各 7 维，共 28 维，但旧字段叫 left_hand/right_hand；当前参考采集代码使用 left_ee/right_ee。body 为 null。info 的 date 为空，只填写了左臂关节名，其他部位名称不完整。相同维度不能证明它就是当前 G1 + Dex3，更不能直接认作完整搬箱行走数据。

尤其需要注意，text.goal 写“取红杯”，但已查看的初帧画面中可见红色方块。这至少说明任务文字与画面需要进一步核验，不宜把它描述为已核实的完整取杯示范。报告将它命名为“官方原始回放测试样本”，仅用来认识回合组织与 state/action 区别。这也可作为后面数据质量检查的直观例子。

如果后续将此旧样本送入当前 G1 Dex3 转换配置，不能只凭文件存在就声称可以直接转换。先明确 left_hand 到 left_ee 等字段对应，再核对关节顺序、语义及相机映射。缺失的硬件和任务真值不能靠改名补齐。[3][5]

五、核验与出处

样本通过官方源码中的外部链接取得，而非从第三方转载取得。固定源码只固定下载入口，Google Drive 文件内容本身不是不可变版本；因此同时保存本次原 ZIP 和 SHA256。原始 JSON 与每个 JPG 解压后与 ZIP 条目字节一致。没有运行下载脚本中的控制程序，没有执行机器人运动。
