# G1 EDU 搬箱任务与数据管线原理

本文讲技术链路。最新产品定义是多设备采集到训练、仿真和部署的图形工作台，见 [产品定位](product/00_先读产品定位与结论.md)；原理实验与完整产品实现的状态应分别说明。

## 从任务而不是从文件格式开始

任务是把桌 A 上的箱子双手抱起，稳定携带一段路，走到桌 B 前，再把箱子放下。它同时要求视觉定位、双臂协调、手部接触、负载下的平衡、移动与放置。训练数据必须覆盖这些决策；把双臂数据存成一个标准格式，并不会获得缺失的行走技能。

建议分层：任务管理器负责接近 A、抓取、抬起、携带、对准 B、放置和撤手；操作策略负责手臂与手；经验证的运动控制器负责站立和行走。操作策略可以与运动控制器协同，但不能让两个进程同时抢同一组关节。端到端全身策略是后续研究选项，初期不宜把它当作已经现成可用的能力。

下面的指标和阈值属于本项目的实验建议，不是厂商承诺。先记录箱子尺寸、质量、抓取位置、桌高、路线和速度，全部在收到设备后按手册允许条件确定。成功定义至少包括：离开 A、全过程不掉落、到达 B、放稳且撤手后仍稳定。分别统计抓取成功率、携带成功率、放置成功率和端到端成功率，分母包括失败与中止回合。

## 43 个关节与 28 维训练动作

43 = 29 个本体关节 + 左手 7 个 + 右手 7 个，是对当前配置的合理推断，仍需实物确认。29 本体中，双腿共 12、腰 3、双臂共 14。普通 G1 Dex3 操作数据只使用双臂 14 与双手 14，所以 `observation.state` 和 `action` 都是 28 维。

29 是物理关节配置，28 是某个学习任务选择的向量长度，SDK 的消息槽数还可能不同。例如源码将 G1 电机消息长度设成 35，这也不能解释成 35 个实际本体自由度。必须区分硬件关节数、消息数组容量、被采集的关节数和被策略控制的关节数。依据见 [S02]、[S04] 和 [S07]。

## 物理设备与运行程序

| 设备 | 运行内容 | 主要输入 | 主要输出 |
| --- | --- | --- | --- |
| Apple Vision Pro | Safari 中的 XR 页面及手部追踪 | 操作者头手运动、机器人图像 | 手腕位姿、手部关键点等 XR 事件 |
| Host 计算机 | `teleop_hand_and_arm.py`、televuer、IK、手势重定向、SDK、EpisodeWriter | XR 事件、DDS 状态、相机帧 | 双臂目标、手部命令、原始 episode |
| G1 的 PC2 开发计算单元 | `teleimager` 相机服务；特定手型另有桥接服务 | 头部与腕部相机 | Host 用的图像流；配置允许时也直接向头显传 WebRTC 图像 |
| 机器人底层控制系统 | 厂商运动控制和状态发布 | SDK 指令、关节反馈、惯性测量等 | 关节动作和 DDS 状态 |
| 关节执行器与传感器 | 驱动与反馈机制 | 电机控制信号 | 真实运动与位置等反馈 |
| 交换机与路由器 | 有线连接及 XR Wi-Fi | 各设备网络数据 | 同一可达网络中的通信 |

厂商底层系统的内部总线、固件线程和具体 PC1/PC2 物理布线没有在本项目中实测。报告应该描述可核实的应用接口边界，不应把应用代码推演成完整电气原理图。PC2 的实际芯片和内存也不能仅凭“配置拉满”确定。

## 四条不同的数据流

第一条是控制流：操作者 → Vision Pro → HTTPS/WSS 上的 XR 事件 → Host。Host 做坐标变换、逆运动学与手部重定向，再通过 SDK/DDS 把双臂和手部命令发给机器人。逆运动学把“手腕希望到哪里”变成“各关节希望到什么角度”；它不是从原始视频直接训练策略。

第二条是关节反馈流：执行器反馈 → 机器人底层状态发布 → DDS 的 `rt/lowstate` → Host 的 SDK 订阅线程。Host 不必先调用 PC2 上的自写转发程序。普通手臂控制类读取 `motor_state[id].q` 和 `dq`；Dex3 手部控制另外处理手部状态。PC2 也能运行 SDK 或整个遥操作程序，但这是部署选项，不代表默认 Host 模式的必要数据通路。[S02]

第三条是图像流：相机 → PC2 的 teleimager → Host 记录；按配置也有 PC2 → 头显的 WebRTC 显示。头显显示流和训练数据流用途不同，不能假定看到的每一帧与记录帧完全相同。头部立体图像在当前录制程序中拆成左右两路，腕部图像另外保存。[S01][S03]

第四条是落盘流：Host 在采样循环中取当前图像、实测关节角、IK 生成的目标角和手部目标 → EpisodeWriter 队列 → JPG 和 `data.json`。一次任务尝试形成一个 episode，不能把相邻帧当作独立实验。

## 控制主题与频率

在核查版本中，普通低层模式发布 `rt/lowcmd`；`--motion` 模式使用 `rt/arm_sdk` 与厂商运动控制协同。订阅主题为 `rt/lowstate`。两种模式切换涉及控制权，不能在不知道当前机器人模式时试运行命令。[S02]

默认录制循环为 30 Hz；G1 双臂控制线程设为 250 Hz。相机帧率、XR 事件频率、SDK 发布频率和模型推理频率可能都不同。录制 30 Hz 不等于每个电机只有 30 Hz 的控制，也不等于传感器之间已经完成硬件同步。

## state 和 action 到底是什么

`state` 是采样时读到的实际关节位置；`action` 是该轮生成的关节目标位置。action 不是“下一个采样时刻实测 state”，更不是电机已经完成的动作。底层跟踪有延迟、限速和误差，故两个向量应分别保存。原始格式有 `qvel`、`torque` 槽，但当前普通录制分支填入的是空数组；不能说它已经采集了速度和力矩。

`body.qpos` 字段也需要看具体分支：手追踪的常见分支为空，某些控制器分支会填本体角度和三维移动命令，甚至动作槽仍命名为 `qpos`。字段名不能替代语义说明。Apple Vision Pro 手追踪配外置 R3 控制行走时，普通脚本不会自动把 R3 的所有移动指令变成训练标签。[S03]

## 采集方案和仿真方案如何汇合

真机输入和仿真输入都要满足相同的任务契约：观察包含哪些图像、状态、时间和任务文本，输出动作控制哪组执行器、采用何种单位和参考坐标系。两者可共用校验、切段、转换、训练与评估接口，但来源标记要保留。

仿真改变灯光和相机再重放同一动作，可以生成视觉变体；改变箱子质量、位置或桌高，则需要重新检查接触与任务是否成功，通常要重新采集或重新求解动作。把失败轨迹渲染得更丰富不能让它成为成功示范。

## 最小项目结构

建议把程序分为 SourceAdapter、EpisodeValidator、Transform、DatasetExporter、Trainer 和 Evaluator。每层产出可读结果：源清单、质量报告、明确的字段映射、训练数据契约、模型与参数、评估记录。初期不用建设复杂数据版本平台，至少保留 source URL、revision、文件 SHA256、转换配置和父 episode ID，这已经能防止“相同文件名但内容变了”的混淆。
