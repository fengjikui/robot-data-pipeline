# 具身智能数据管线工作台 PRD 共创稿

版本：0.5 · 讨论共识与首轮实现范围。创建：2026-10-30；更新：2026-10-31。

本文承接旧版 PRD、报告及 v0.2.0 原型，记录会后重新明确的目标。**“已确认”来自用户明确表述；“建议”是待讨论的方案；“待定”不作为开发承诺。** 本轮先确认能力，再进行 UI/UX 设计，最后进入实现；本稿不代表功能已交付或设备已验收。

## 1. 执行摘要 Executive Summary

### 1.1 问题与价值

操作者已有具体任务、机器人和训练方法，却仍需要在多台设备上启动程序、整理回合、找文件、对参数、追查错误。采集结束到下一次实验之间缺少连贯交接；外部数据也难以按任务筛选和复用。

工作台围绕一次任务迭代，管理**数据从哪里来、哪些能用、如何处理、用哪份数据训练、效果怎样、下一轮改什么**。底层复用厂商工具和训练/仿真后端，上层统一任务上下文、阶段操作、依赖关系及结果追踪。

### 1.2 本轮已确认的范围

| 项目 | 已确认内容 |

“仿真采集”和“仿真评估”分别管理：前者产生示范数据，后者运行训练后的策略、观察环境反馈并形成任务结果。示范回放不能替代策略闭环评估。

### 1.3 第一阶段成功标准（验收规则建议，具体测试规模待定）

1. 真机与仿真两种采集后端均能完成：准备 → 录制 → 停止 → 保存确认 → 自动登记回合 → 后台排队质检；连续采集无需逐回合手工找目录导入，也不必等上一回合质检结束才进行下一回合。
2. 用户可从回合库选定输入，单独使用真机或仿真数据，也可明确组合两者；完成检查、筛选和训练输入准备，不必手工拼接已接入阶段的目录或命令。
3. 指定训练后端真实加载所选数据并完成训练，生成包含模型、配置与数据来源的产物包；首批读取验收不能替代训练完成。
4. 训练所得策略在匹配的仿真任务中真实执行，保存评价条件、成功/失败结果、指标与录像。成功率阈值在具体任务和基线确定后约定，不预先编造。
5. 每次运行可追溯到输入、配置、日志和输出；失败时保留已完成产物，能够定位问题并从适当阶段继续。

软件链路验收与策略效果验收分别报告。管线运行可靠，不意味着模型已达到搬箱要求；效果不足时仍须记录失败、形成下一轮补采或调整的依据。

## 2. 用户体验与功能 User Experience & Functionality

### 2.1 用户与主线

首期由同一个操作者承担任务负责人、数据采集者、数据整理者和训练使用者四种工作角色，不因此引入四套账号或权限系统。

以搬箱为例：定义“桌 A 取箱 → 搬运移动 → 桌 B 放箱”的目标与成功规则，选择目标本体和控制配置；从真机采集、仿真采集、外部数据中取得候选回合；检查并整理为明确的数据版本；按已支持配方转换和按需增强；训练并仿真评估；根据失败结果选择补采、调整数据或调整配方，再进行下一轮。

**完整搬箱仍是原目标。** 若工程里程碑只完成原地抓放，应按实际范围命名，不能算完成含行走的搬箱任务。学习策略、导航/移动目标和低层控制器各自负责什么，必须在任务配置中说明，不能从只有上肢的数据中虚构腿部动作。

### 2.2 功能模块与用户故事（首期范围建议）

这些是能力分组，不直接等同于页面数量或菜单结构。

| ID | 用户故事 | 必须达到的能力 | 怎样判断完成 |
| --- | --- | --- | --- |
| F01 任务与配置 | 作为操作者，我希望保存本轮目标与配置，避免每次重填 | 任务、成功规则、本体/手部/相机、遥操作方式、执行机、训练配方；首次配置与重复使用分开 | 重开任务可恢复配置；修改目标不会改写旧数据的真实来源和旧作业快照 |
| F02 真机采集 | 我希望从工作台准备遥操作并连续录制回合 | 连接/依赖预检、准备或复用服务、头显待办、跟随状态、开始/结束回合、保存确认、自动入库和后台质检 | 区分录制/保存/归档/质检状态；保存确认后登记，质检不阻塞下一回合；下游按检查与审查条件引用 |
| F03 仿真采集 | 我希望在仿真场景中产生同一任务的示范 | 选择本体/场景/控制器、启动场景、连接操作者输入、复位、录制、自动入库和后台质检；保存场景条件和种子（后端提供时） | 可连续复位采集；回合保留仿真来源、时间和场景版本；质检不阻塞下一回合；不占用真机通信目标 |
| F04 数据获取与资产 | 我希望找回自己已有的数据，并导入适合任务的外部数据 | 从已适配来源的地址/ID读取元数据、筛选并下载；导入本地目录；登记来源/版本/使用条件；检索与预览 | 明确筛选结果与实际下载文件，知道持有的是样本、子集还是全量；重复使用可找回同一批数据并接入后续训练流程 |
| F05 检查与整理 | 我希望知道问题在哪些回合，并决定保留哪些 | 文件/数值/时间/语义检查；图像与 state/action 对照；成功、失败和接管标记；排除、切段、训练划分 | 结论定位到回合或时间段；未经检查的项目保留未知；失败回合不等同于坏文件，也不默认删除 |

| F07 训练与仿真评估 | 我希望明确用哪些数据训练，并查看真实任务效果 | 选择固定数据版本和配方；运行位置/参数；启动、停止、日志与模型；固定评估条件、闭环执行、录像与失败分类 | 数据→训练→模型→评估一一关联；评价使用本次指定的模型；公开策略、回放与自训模型结果分别标明 |
| F08 管线运行与迭代 | 我希望阶段之间自动交接，失败后可继续 | 独立执行/选择串联；按真实状态交接产物；人工审查暂停；日志、定位、重试、取消、刷新恢复 | 不靠固定延时判断成功；缺少前置条件不启动；能从失败阶段恢复，原始数据和已成功产物保留 |

### 2.3 两种采集方式怎样统一

建议上层统一“会话、回合、开始/结束、保存、预览、结果、入库”操作；下层分别接真机与仿真适配器。

- 真机侧关心硬件与网络、相机、控制模式、真实反馈、现场操作和保存。
- 仿真侧关心环境启动、场景/初始条件、时间推进、复位、控制器、传感器与保存。
- 保留原始后端文件，不承诺两种来源天然同格式。统一入口清单包含任务、来源、设备/场景配置、观察、实际状态、目标动作、时间信息和结果；缺失项如实标明。
- 控制、录制和服务进程有不同生命周期。结束一个回合不等于退出遥操作；“保存完成”与“收到停止命令”是不同事件。
- 仿真与真机通信目标须明确区分；不能只用同一个机器人型号决定运行目标。

#### 2.3.1 日常连续采集流程（节奏已确认，操作细节建议）

首次连接、安装与标定保存为设备/环境配置。日常使用建议沿以下路径复用，具体交互控件留到 UI/UX 阶段决定：

1. 选择任务及真机/仿真配置，恢复本轮任务、设备、记录位置和采集参数。
2. 预检并准备或复用服务，显示需要操作者在头显或现场完成的步骤；仿真模式另准备匹配场景。
3. 操作者明确启用遥操作跟随，再开始录制本回合；服务就绪、控制跟随和录制分别可识别。
4. 结束本回合后显示保存进度；记录器确认落盘完成，再自动归档登记并排队质检。
5. 记录器可接收下一回合时，操作者可继续采集，不必等待后台质检；仿真按任务进行复位。这里不要求尚未写完的记录器强行并发录制。
6. 结束整次采集会话后，集中预览和筛选回合，再形成待确认的训练数据版本。待处理队列及每个回合的状态可继续查看。

采集/保存、归档/传输、质检、任务结果分别记录。例如“文件已保存、质检排队中、搬箱结果待标”可以同时成立，不能用一个笼统的“成功”覆盖所有结论。

后台队列优先保障采集：资源不足时等待或降低并发；不因新回合入库自动启动训练。单回合质检不通过时保留数据和问题，不自动删除或结束整个采集会话；持续出现采集异常应及时提示操作者。

验收建议：连续多个回合无需手动导入；旧回合检查时可以录制新回合；重复保存完成事件不重复登记；刷新后能够找回回合、队列和结果；保存/归档不完整的回合不被提前选为已验收的训练输入。

#### 2.3.2 回合任务结果标记（已确认）

已确认支持成功、失败、中断和待标，允许结束回合时快速标记，也允许采集后补标或批量整理。任务结果与文件/结构质量分别显示：例如文件完整但箱子掉落，可同时是“结构通过、任务失败”。

仿真任务具备已确认的成功规则时，可保存环境规则的判定；人工标记与自动规则结果分别记录来源和依据。规则未配置、证据不足或结论冲突时保留待核实，不因录制正常结束自动认定任务成功。

失败回合保留原件、任务结果和失败原因，供筛选、诊断或后续适用配方选择；是否进入某次训练由数据选择和训练用途决定，不把任务失败等同于坏文件，也不默认删除。

### 2.4 数据怎样成为本轮训练输入

建议区分四个对象：原始回合（证据）→ 数据选择/切段视图（引用）→ 转换或增强产物（派生）→ 固定训练数据版本（训练输入）。这是用户可理解的关系，不要求先建设重型数据版本平台。

用户应能回答：这次用了哪些回合、排除了什么、如何划分、经过哪些处理、来自真机还是仿真。允许回滚选择和复用产物，不因改一个标签复制整个数据集。

**已确认：真机和仿真数据分别入库，用户可明确组合为同一次训练的输入。** 单独使用一种来源也应可行。组合是训练数据的选择，不改写来源资产；每个回合保留来源、原始配置和处理记录。

建议形成可复用的训练数据视图/版本，例如“真机 A 批 + 仿真 B 批 → 训练数据 V1”。下一轮修改回合选择形成 V2，旧训练和模型仍指向 V1。允许引用已有媒体，不要求为每次组合完整复制数据。

组合前核对任务用途、本体/手型、观察与动作语义、相机及时间配置，并显示可直接使用、需要已支持适配、缺少依据等结论；文件格式相同本身不是放行依据。用户能看到选中了哪些来源、回合与数据量，以及哪些被排除、为什么排除。

**已确认：支持来源采样比例设置，默认按可用训练样本分布。** 回合数量、有效帧数与训练样本数分别展示；自定义采样不增加原创数据。权重只影响训练部分，验证/测试的留出清单独立固定。外部数据是否支持同样的混合方式，按具体来源及适配范围另行确认。

#### 2.4.1 找到候选与预览

建议围绕当前任务、本体与配方，按来源、原始数据任务、任务结果、结构质量、采集批次/时间和标签筛选。关节/相机等关键配置缺失时保留未知；发现不兼容时说明原因，不把格式或标签当成可训练证据。

点击回合只切换预览，明确的选择操作才将其加入本轮数据。切换筛选不清空已有选择；可看出已选项目中哪些不在当前筛选结果里。列表将任务结果与数据质量分别显示。

预览至少包含相机图像、帧位置、实际 state、目标 action、任务和问题位置；缺少实际时间戳时保留未知，可按标称 FPS 展示估算时间并说明依据。

#### 2.4.2 整回合选择与手动切段

已确认支持整回合选择和手动切段。片段保存源回合 ID、半开帧区间 `[start,end)`、名称/用途和原始来源，不覆盖源文件。保留所有图像、状态、动作之间的原始对照，不把不连续片段直接拼接成一条连续动作轨迹。

同一来源的整回合与其片段重叠时要提示重复计数，并提供替换/移除选择；新片段不能自动把父回合改为任务成功。局部抓取片段用于子任务时，记录其用途，不能标成完整移动搬箱的成功示范。

片段短于目标配方所需的时间窗口、引用缺图或存在非法动作时，在所选范围内重新核查并定位问题。父回合其余部分有问题与当前片段是否可用分别呈现。

#### 2.4.3 组合、采样与分组划分

组合摘要展示选中的回合/片段、有效帧数、来源分布、重复和阻断项。自然分布与自定义来源权重两种模式必须保存并真实传入已支持的读取/训练适配器；后端不支持时明确指出，不把保存参数当成实际生效。

划分建议以原始回合为最小分组，同一母回合的片段与增强版本跟随该组；跨资产重复导入的相同源内容也要识别，避免仅按资产 ID 划分。同一分组不同时出现在训练与留出集合。可按评估目标进一步采用采集会话/场景留出，具体规则需要明确，避免把相邻帧随机分到两边。

提供可调整的训练/验证/测试比例、固定随机种子和划分预览，不预先把某个百分比当作所有任务的标准。组数不足时说明问题，用户可明确选择仅训练；界面需说明此时没有离线留出验证。

若归一化统计由本轮数据估计，只用训练部分估计；验证/测试复用对应变换。若配方采用冻结的预训练统计，记录其来源。随机训练增强用于训练部分，稳健性评估所需扰动由独立评价方案定义。这些是根据数据泄漏防范原则制定的本项目规则。[数据泄漏与预处理](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage)、[按领域分组划分](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.GroupShuffleSplit.html)。

#### 2.4.4 确认与训练输入准备

保存筛选规则便于下次复用；确认的数据版本则冻结明确的回合/区间、源指纹、标记快照、划分和配置。后来采集或修改标签不会改变旧训练输入。用户修改已确认选择时另存新版本，旧训练、模型和评价继续关联旧清单。

确认摘要包含名称、任务/本体、来源组成、选数及排除原因、划分、采样规则、目标读取器、预期产物和缺项。用户确认后才进入后续自动构建；转换或读取发生阻断错误时保留选择，修正后重试。

“准备包生成”“项目契约读取验证通过”“指定训练器读取验收通过”分别显示。只有真正运行指定训练器读取器并验证输入，才能标记该组合可用于相应训练；自有 JSONL 的读回不替代 LeRobot 验收。

建议验收覆盖：跨来源筛选后选择仍在；片段精确对应源帧且原件未变；权重改变实际训练抽样；同源片段不跨集合；确认后旧版本不变；失败或刷新后能找回选择、作业和产物。

### 2.5 自动处理与人工确认（原则已确认，执行细节待细化）

**已确认：选择自动串联时，在关键节点等待人工确认，其余满足条件的步骤自动继续。** 默认确认点为新训练数据版本，以及首次使用或关键参数变化后的增强配方审查。独立阶段按钮继续保留；阻断错误、缺少前置条件或状态未知时暂停并显示原因。

| 环节 | 系统负责 | 人工介入规则 |
| --- | --- | --- |
| 结构质检 | 每回合保存入库后排队检查缺失文件、异常数值、索引与维度，生成定位明确的报告 | 采集后集中处理阻断问题或排除相关回合；系统保留原件，不默认删除数据 |
| 任务质量与选数 | 提供回合预览、成功/失败/接管标记、筛选与批量操作 | 确认本轮选择的数据；任务失败和文件损坏分别处理，不能直接等同 |
| 格式转换 | 按经过验证的模板执行、记录映射并进行训练读取验收 | 已验证的兼容配置自动复用；映射或动作语义缺少依据时暂停，提示补齐配置或验收证据 |
| 数据增强 | 为新配方提供抽样前后对照，记录参数、来源与派生关系 | 首次使用或关键参数变化时确认配方，再批量生成或在训练时使用；不要求逐帧审批 |
| 训练与仿真 | 使用明确的数据版本、训练配置和评价方案执行并保存结果 | 按用户选择的启动/串联规则运行，遇到阻断错误或未知状态暂停并显示原因 |

确认记录绑定具体的数据版本或增强配方及其配置，而非一个可随意变化的目录名。建议记录所选来源/回合、排除与划分规则、配方参数及审查样例；详细字段在后续设计中细化。

相同且仍有效的对象可复用已有确认。因本次运行失败而重试，不应仅因重试这个动作重复审批；输入或关键配置改变后，需要复查受影响的确认。自动串联恢复前仍检查依赖和当前状态。以上是已确认原则的执行建议，尚不是当前程序已有的审批能力。

### 2.6 外部数据获取与后续衔接（范围已确认，细节建议）

已确认首期提供“指定来源下载、筛选、入库＋本地目录导入”。指定来源包括首批已适配的数据集地址/ID或交付位置，不能将所有网址都标成可自动识别、筛选和下载。

建议的用户流程：

1. 指定来源，或选择已收到的本地目录；登记原始来源、本体/手型、任务、格式/版本及使用条件。缺少的字段显示待确认，不用当前目标任务替来源填写事实。
2. 读取可用目录、元数据或样本预览，按来源提供的信息筛选任务/回合；筛选能力按具体数据集布局声明。
3. 展示拟获取的回合范围、实际要传输的文件、大小或未知项、执行机与存储位置，用户确认后执行。
4. 跟踪下载/导入进度与完成清单，校验成功后入库；中断保留已完成部分，恢复时核对版本和文件，不把部分下载称为全量到齐。
5. 对取得的数据运行已支持检查，选入训练数据版本；与自采数据复用相同的处理、审查、训练及仿真评估流程。

**筛选范围与实际下载范围分别展示。** 某些来源需要按文件/分片下载，再在本地筛选回合；上游不提供对应粒度时，平台说明实际需要下载的范围，不承诺只传输选中的帧。缺少元数据时可先获取约定样本核验，不能编造任务或关节含义。

已经采用目标训练格式的数据，可以在完整性、语义及读取验收通过后复用，跳过不必要的重新打包；原始录包或异构格式按已支持适配路径处理。动作语义不明、缺少必要字段或缺少适配器时，显示阻断原因及下一步需求。

验收建议：对首批支持清单中的一个实际来源完成指定范围获取、入库、筛选和训练读取验收；选定数据可进入第一阶段训练/仿真路径。再次使用时保留来源版本、持有范围、选择规则与产物关联。

当前原型的 128 MiB 本地导入限制属于后续需要改造的实现边界。正式首期的数据规模、磁盘预算和性能指标以选定任务样本制定，不沿用原型上限，也不预先宣称支持任意规模。

### 2.7 首期暂不纳入的扩展（建议）

- 同时接入所有厂商、本体、输入设备和策略；先维护少量经过验证的支持组合。
- 自动搜索全互联网、自动判断任意来源可训练、自动完成跨本体动作迁移。
- 多用户审批、机器人集群、多租户与通用拖拽流程编辑器。
- 自动生成真实关节动作、自动伪造任务标签或把增强数据直接当成人工验收通过。

真机部署、更多本体、规模化数据仓库属于后续阶段；接口边界在本期保留。

## 3. AI 系统需求 AI System Requirements

### 3.1 策略与工具

训练配方应声明支持的数据格式版本、观察和动作定义、图像通道、时间窗口、归一化方式、模型与依赖环境。首期接入一种能与任务和仿真环境形成闭环的策略组合，具体选型待定；后续增加策略时复用已有任务、数据、运行与产物记录。

工具分工为采集适配器、仿真环境适配器、数据读取/检查器、转换器、增强器、训练器和评价器。平台编排这些组件；机器人实时控制仍留在适当的本地控制系统中。

AI/agent 可作为质量或增强审查的辅助能力，但首期不依赖大模型 API 才能运行。若后续加入，结论要能定位到证据、保留来源，并区分建议与人工确认；当前不预先绑定服务商。

### 3.2 验证与审查

- 数据：结构、时序、标定/语义、任务质量分别记录；无法检查不等于通过。
- 增强：训练时随机变换审查配方和抽样预览；离线生成保存原件对照与结果抽检。默认人工节点遵循 2.5 节已确认原则，具体抽样数量和审查字段待细化。
- 训练：保存固定数据选择和划分、配置及读取证据，避免同源回合和派生版本跨集合泄漏。
- 仿真：预先固定任务成功规则、初始条件集合、评价次数和失败分类；数值规模待环境基线确认。
- 管线：验证重复点击、保存中断、断连、空间不足、后端报错和页面刷新等情况；本次讨论不实际执行这些测试。

## 4. 技术规格 Technical Specifications

### 4.1 架构与共享对象（设计建议）

工作台 → 管线编排服务 → 执行机上的适配器/工具。工作台可在 Mac、Windows、Linux 使用；厂商采集器和 GPU 仿真/训练按各自已支持的环境运行。界面所在机器的路径不能替代执行机路径。

共享对象先收敛为 Task、Robot/Teleop/Sim Profile、Episode、Dataset View/Version、Recipe、Run、Artifact、Model 和 Evaluation；具体字段与接口在功能范围确认后细化。

每个阶段描述输入、前置条件、配置、执行位置、状态、输出及恢复方式。自动串联依赖前一步确实完成并登记的产物，而非拼接命令和目录。

建议公共状态：待准备、就绪、运行中、等待人工、保存/整理中、完成、失败、取消、状态未知。不同阶段保留必要子状态；未知状态先对账，不盲目重复有副作用的操作。

### 4.2 数据、连接与运行约束

大文件保留在受管理目录/存储中，数据库保存索引与关系；原始数据不覆盖。初期可增量扩展当前实现，不在 PRD 阶段锁定新的前端、调度器或存储产品。

远程工作站视为可提供的前提，但地址、系统和 GPU 型号在接入时核对。凭据不写入任务模板、数据元信息或日志。只管理本任务注册的进程；作业运行前与运行中检查资源，采用保守并发。实时控制和本地退出策略不依赖网页每次请求及时到达。

### 4.3 当前实现基线（已查代码）

本轮开发前的源码 v0.2.0 已有任务式界面、本地资产导入/快照、来源和标签、限定范围的 Unitree 28维结构质检、自有 JSONL 导出、采集配置保存、作业日志与输入快照。

当前尚无真实采集服务编排、仿真采集执行器、官方训练格式转换、增强执行、训练或仿真评价后端。已有界面和自有 JSONL 不作为上述能力完成的证据。后续应复用已有有效基础，避免把原型布局当成最终需求。

## 5. 风险与路线图 Risks & Roadmap

### 5.1 里程碑建议

| 里程碑 | 交付和验收范围 |
| --- | --- |
| 本轮需求与设计 | 完成 PRD 共识、支持范围和验收表；随后完成用户流程、状态及 UI/UX；开发排期待范围明确后制定 |
| M1 双采集入口 | 真机与仿真共用会话/回合操作，分别完成准备、录制、保存确认、自动登记、后台质检与预览；外部数据保留入库入口 |
| M2 可训练数据 | 回合选择、分层检查、适配/转换、按需增强、固定划分及实际读取验收；限定外部来源逐项接入 |
| M3 第一阶段终点 | 实际训练与仿真闭环评价，关联模型、数据与结果，能依据失败开始下一轮迭代 |
| M4 真机部署 | 另行定义部署包、兼容性、控制接口、启停与现场任务验收 |
| 后续扩展 | 更多来源/本体/策略，以及随真实数据规模演进的数据仓库和加载优化 |

M1、M2、M3 是第一阶段内部的工程里程碑，不改变已确认的第一阶段终点。现阶段不编造人日、完成日期、GPU 适配结论或任务成功率。

### 5.2 关键风险

- 真机与仿真手型、相机、动作语义、控制频率不同：建立明确配置与映射，不能只按维度判断兼容。
- 完整移动搬箱需要匹配的控制范围与评价场景：单独验证移动目标、上身策略与低层控制器的职责和接口。
- 后端只给切换命令或进程状态：需补录制状态和保存完成确认，不能重复切换来盲目恢复。
- 数据格式转换完成但训练器不能正确读取：以真实读取和后续训练验收，不以目录存在放行。
- 模型效果不佳：保留完整失败证据；是否达到任务指标按具体验收规则报告。

### 5.3 接下来共同确定的问题

1. 已确认逐回合入库、后台排队质检，以及当场/事后标记；继续完善首次配置与异常恢复的具体动作。
2. 已确认整回合选择、手动切段、来源比例设置，以及指定外部来源获取；继续确定首批支持清单、配方与数据规模。
3. 已确认关键节点人工确认、其余自动继续；进一步明确确认对象的变更、继承、重试及恢复细节。
4. 首个训练/仿真任务组合、控制范围与指标怎样收敛？
5. 对应关键流程与异常状态确定后，再进入页面结构与 UI/UX。

本轮已获用户授权：组织 agent 共同审查、收敛方案，设定实现目标后直接开发。首个软件迭代聚焦回合级数据准备的真实路径，采用三步任务区“选回合与预览 → 组合与划分 → 确认并准备”。真实采集、官方训练器、GPU 闭环仍按第一阶段总体路线逐项接入；本轮数据准备交付不代表第一阶段全部验收完成。
