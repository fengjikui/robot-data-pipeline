# G1 一键采集需要组织哪些设备和服务

这是未来工作台的接入设计，不是已实现的一键启动脚本。固定核查版本为 `xr_teleoperate@817fb00c63cde15e5f24a0f8fa08e1e33ed89d3b`。硬件先按 G1 29 本体加 Dex3 双手研究，最终以到货清单为准。[R01][R02]

G1 是首个采集后端；更换本体后的通用操作、输入/控制/视频与记录适配方向，另见 [跨本体采集接口初步调研](08_跨本体遥操作与采集接口初步调研.md)。本文件不作为其他型号的直接操作手册。

## 一键之前与一键之后

第一次要完成设备登记、厂商 SDK/环境安装、网络连接、相机配置、标定、Vision Pro 证书信任以及控制模式验证。工作台可以提供检查和安装任务，但不能假装物理开机、佩戴头显、授予追踪权限和现场模式准备都由一个软件按钮完成。

以后使用时，一键的目标是：按保存的设备配置启动本次需要的服务，检查真实输入和状态，把用户引导至可遥操作/录制的状态。已经运行的厂商基础服务只检查和复用；不能为了方便把整机软件栈全部重启。

## 各设备承担的服务

| 位置 | 服务或能力 | 本次启动策略 | 证明已就绪的依据 |
| --- | --- | --- | --- |
| 机器人底层控制单元 | 厂商运控与状态发布 | 检查，按所选控制模式接入；不默认重启或替换 | 读取状态、版本与控制模式；知道实际控制权归属 |
| PC2 | teleimager 相机服务 | 检测已有兼容实例；没有才由受控执行器启动 | 相机配置正确；每路得到持续更新的帧；头部显示服务按配置可达 |
| Host | SDK 只读状态探测器 | 可独立启动 | 指定网卡与 DDS 域匹配；关节状态持续到达；不创建命令发布者 |
| Host | 遥操作主进程、televuer、IK 和手部重定向 | 在用户启用遥操作时启动 | IPC 心跳、XR 输入、图像与控制状态组合检查，不单看 PID |
| Vision Pro | Safari XR 页面 | 显示访问入口与人工待办 | XR 会话建立且追踪数据持续到达；网页存在不等于会话成功 |
| Host | EpisodeWriter 或其适配接口 | 随采集会话准备，按回合录制 | 实际写入、结束、队列完成、输出文件齐全，并登记回合清单 |
| 机器人侧或外设侧 | 手部辅助服务 | 依手型选择；Dex3、Dex1、Inspire 等不共用同一启动清单 | 对应手部状态与命令接口匹配，不盲目启动另一个手型的桥 |
| 仿真执行机 | 匹配本体的任务场景、DDS 与图像接口 | 仿真采集模式启动；不同时指向真机 | 仿真时间在推进、传感器可用、任务可重置，DDS/网络已隔离 |
| 训练机 | 转换、训练和评估执行器 | 数据阶段完成后按作业启动 | 依赖和资源检查、日志、实际输出及后端健康状态 |

这里的执行器是未来工作台管理本机/远端作业的小组件，不等于让它承担实时机器人控制。它可以在已授权环境中通过 SSH、受控服务接口或本地进程管理工作；具体方案在工程实现时选择。

设备职责和现有上游服务依据 R01、R16；表中的检查、执行器和状态汇总是拟新增的工作台能力。[R01][R16]

## 默认时序

1. 用户选“G1 设备档案 + 真机/仿真 + 任务 + 遥操作配置”。
2. 工作台检查网络、版本、输出目录、磁盘、控制模式及相机/手型匹配。
3. 若是仿真，先启动匹配场景；若是真机，显示必须在现场完成的准备条件。
4. 启动或复用所需相机服务，运行只读状态和图像探测。此时应不产生动作控制；仿真模式读取的是仿真传感器与关节状态。
5. 用户选择“启用遥操作”；工作台说明该步骤会启动控制相关程序，按已核实的厂商流程取得控制权。
6. 提示用户在 Vision Pro 进入 XR 会话，检查输入、姿态对齐和所选动作范围。不能用固定等待 5 秒代替状态检查。
7. 满足条件后进入随动状态，显示“开始录制”；按回合开始/结束保存，成功或失败由人工或独立评价机制标注。
8. 结束本次采集时先结束回合并等待保存，再按所选控制模式退出遥操作并释放本次占用。通用后台基础服务是否保留由模板决定。
9. 数据变为已完成产物后，用户可以按检查、增强、转换、训练等阶段按钮继续，或运行已经保存的串联模板。

## 已发现的启动副作用

当前宇树脚本在进入等待 `r` 的循环之前，会创建控制相关对象；普通非 `--motion` 分支会尝试进入 Debug 模式，G1 手臂控制器初始化会建立电机命令并启动发布线程。因而“进程已启动、尚未点击 r”不能被界面解释为“只有只读连接、完全没有接管”。这一点是对源码的判断，尚未实机测量。[R01]

设计上应提供真正独立的只读探测。若工程上把全部准备包在一个“启动遥操作”按钮内，按钮要包含并显示控制准备阶段；不能给它起“仅连接”这样的名字。相机预览、控制接管、跟随运动、录制是可区分的状态，即使界面用一个向导组织它们。

## 官方 IPC 是可复用入口

当前脚本提供 `--ipc`。`teleop/utils/ipc.py` 通过本地 ZeroMQ IPC 提供命令与心跳，定义 `CMD_START`、`CMD_STOP` 和 `CMD_RECORD_TOGGLE`；主程序心跳返回 `START`、`STOP`、`READY`、`RECORD_RUNNING`。[R02]

因此接入方案优先使用结构化 IPC，不依赖向终端模拟按键。但要注意：

- 接口是 Host 本地 IPC，不是一个可以从浏览器直接调用的远程 HTTP 服务；需要 Host 适配桥。
- `CMD_START` 对应跟随启动入口，不代表整个环境已安装、所有服务已准备或数据已经录制。
- `CMD_STOP` 对应程序退出流程，不是独立硬件急停接口；界面不能将它标为“硬件急停”。
- `CMD_RECORD_TOGGLE` 不是幂等的“设置录制=true”。它是翻转请求，盲目重试可能把正在录制变为结束。
- 源码的返回答复只表示命令处理函数已被调用，不能证明某个 episode 已完成写入。
- IPC 模块说明中的心跳例子与主程序实际 `get_state()` 字段有差异；适配器按固定程序实现核对，不复制示例猜状态。

## 工作台需要补充的接口语义

| 面向工作台的意图 | 桥接层如何实现 | 什么时候才显示成功 |
| --- | --- | --- |
| 准备环境 | 检查并启动依赖，逐项探测 | 服务及数据面检查均满足模板要求；人工未完成项单独显示 |
| 启用跟随 | 在正确状态下发送 START，并核对输入/控制状态 | 主程序状态转换已观察到；仍要分开记录是否有新鲜 XR 输入 |
| 开始录制 | 先查状态，只在未录制且可开始时发送一次 toggle | `RECORD_RUNNING` 实际变为 true，并观测新回合创建 |
| 结束并保存 | 先查状态，只在正在录制时发送一次 toggle | 录制停止，写入完成，目录检查与产物登记完成；不以 ACK 当保存完成 |
| 结束遥操作 | 在可退出状态发 STOP，跟踪程序退出及控制释放 | 上游按预期结束；如无法核实控制权，显示“状态未知，需检查” |

若 ACK 丢失，先重新查询真实状态；不要直接重发 toggle。若原始程序没有完整保存查询，需要小范围扩展记录器的完成事件/manifest 或在适配器中做明确的保存完成观测。仅见到 `data.json` 文件存在不足以放行，因为它可能还在写入。

## 为什么需要状态而不是一串 shell

启动链路至少会遇到：PC2 连不上；相机设备忙；DDS 有状态但读到了另一台机器人/仿真；证书不匹配；头显未进入会话；控制模式冲突；录制停止但写盘未完成。每一项都需要知道在哪个设备上发生、是否可重试、哪些已经启动、是否有控制副作用。

建议会话状态分为：未连接 → 只读检查 → 环境就绪/等待人工 → 控制准备 → 等待 XR → 随动 → 录制 → 保存 → 随动 → 释放控制 → 已结束。任一步均可失败或变为状态未知。按钮的可用性取决于状态与能力，而非用户是否已经点击过上一个按钮。

## 停止与恢复规则

“结束回合”“结束遥操作”“取消训练”“停止仿真”和“机器人紧急停止”分别显示，不共用一个含义模糊的 Stop。工作台断开、Host 异常和 PC2 异常需要本地适配层/控制器负责的超时策略；不能假定网页还活着才能让机器人停止。

重试只处理本次注册的作业与依赖；复用的厂商基础服务不随意终止。镜像/SDK 安装、证书配置和固件升级属于独立初始化任务，不在每次采集时自动重装或升级。

## 首轮 G1 适配验收

先在模拟执行器中验证成功、超时、断线、重复点击与恢复；再做真实只读连接；再按厂商流程验证控制启停；最后验证完整回合保存。每次实机试验只开放已经验收的控制范围。单人操作是软件产品范围，不意味着取消厂商要求的现场保护或人员安排。

普通 28 维双臂双手记录与未来的全身抱箱移动要用不同配置和验收。前者成功不能让工作台直接给后者显示“已支持”。
